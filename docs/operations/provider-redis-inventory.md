# Provider Redis inventory

What still talks to Redis for Google provider work, why, and what it would cost to remove or replace each piece. Written for the owner's decision on the dedicated provider Redis. Nothing here changes behaviour.

## The three Redis instances

| Instance                                          | Env var                        | Holds                                                                            | Persistence                                                                                             |
| ------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Provider Redis (`services/google-provider-redis`) | `PROVIDER_EPHEMERAL_REDIS_URL` | Google provider ephemeral state and egress coordination                          | None: `--appendonly no`, `--save ''`, `noeviction`, 256 MiB, TLS only, ACL limited to four key prefixes |
| App Redis                                         | `REDIS_URL`                    | Rate limits, health state, some provider-adjacent counters and locks (see below) | Provider-managed                                                                                        |
| Queue Redis                                       | `QUEUE_REDIS_URL`              | BullMQ queues, job runtime observations                                          | Provider-managed                                                                                        |

The provider Redis ACL (`services/google-provider-redis/entrypoint.sh`) allows exactly `provider-ephemeral:*`, `google-provider:*`, `oauth-callback:*` and `google-admission:*`. Boot verification (`src/shared/provider-ephemeral/runtime-verification.ts`) refuses a Redis that persists, replicates, evicts, or is not the expected size. The server keeps nothing across a restart; every reader treats a missing value as a restart or an expiry.

## Live Redis calls on the provider Redis

Wiring: `src/composition/google-provider-authority.ts` builds one client (`createProviderEphemeralRedis`) and passes it to the ephemeral store and, in production, to the egress runtime (`src/composition/google-egress-runtime.ts`). Local and test stacks fall back to the app Redis or an in-memory store.

### A. Ephemeral store (`src/shared/provider-ephemeral/provider-ephemeral-store.ts`)

Key pattern for every row: `provider-ephemeral:{<namespace>}:<key>`, key matching `[A-Za-z0-9_-]{32,128}`, value at most 5 MiB, TTL 1 to 86,400 s. Operations: `SET EX NX`, `GET`, `GETDEL`, `DEL`, `INFO server` (restart detection), and compare-and-swap Lua scripts.

| Namespace                           | Lifetime           | Owning feature                                                                                                           | What it coordinates                                                                          | Cost to remove or replace                                                                                                                 |
| ----------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `oauth-state`                       | 10 min, single use | Google connect (`integration/application/oauth-state-handle.ts`)                                                         | Holds the PKCE verifier and OIDC nonce behind the opaque state handle; redeemed once         | New Postgres table plus a redeem-once transaction and a sweep. Moderate. A lost row only fails one in-progress connect                    |
| `opaque-reference` (review cursor)  | 30 min             | Google review sync paging (`integration/infrastructure/google-review-cursor-store.ts`)                                   | Page cursors, run index and org index, written together by `compareAndSwapMany`              | Table with rows per cursor plus the same atomic multi-row swap; the multi-key swap and tombstones are the hard part. Largest single piece |
| `opaque-reference` (push reference) | 15 min             | Google review push notifications (`integration/infrastructure/google-review-push-reference-store.ts`)                    | One-shot reference a push receipt redeems into a targeted fetch                              | Small table; a Postgres receipts store already sits beside it (`gbp-review-push-receipt`). Small                                          |
| `authorization-lease`               | At most 30 s       | Every Google provider call that needs a lease (`provider-ephemeral/authorization-lease.ts`)                              | Short grant that a call holds between issue, renew and use; revalidated against Postgres     | Table with expiry and a sweep, but every Google call adds a write on the hot path. Moderate, with a latency cost                          |
| `invalidation-dedupe`               | 24 h               | Authorization invalidation fan-out (`provider-ephemeral/authorization-invalidation.ts`, wired in `integration/build.ts`) | Claims an event once across handlers, with owner takeover, so a revoke fans out exactly once | Outbox receipts already exist in Postgres (`outboxRepo`); the dedupe could become a receipt claim. Small to moderate                      |

The Google import reference handoff no longer uses this store: it is Postgres-backed (`integration/infrastructure/durable-import-reference-store.ts`). Its authorization lease and invalidation handler still use rows A above.

### B. Egress coordination (`src/shared/google-provider-control/quota-coordinator.ts`, `redis-coordination-scripts.ts`)

Created in `google-egress-runtime.ts`; admission permits themselves live in Postgres (`postgres-permit-authority.ts`), only the rate and concurrency counters live in Redis.

| Key pattern                                                                                            | Lifetime                                                            | Owning feature                                                  | What it coordinates                                                                    | Cost to remove or replace                                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `google-provider:{coordination}:quota:<policy>:<bucket>:<sha256>` (hash: binding, tokens, updatedAtMs) | `PEXPIRE` between 60 s and 24 h, about twice the bucket refill time | Google quota policy (token bucket per route policy and binding) | Keeps web and worker from jointly exceeding Google's per-project and per-binding rates | Postgres row-lock token bucket: one locked write per Google call, contention across web and worker. Per-process buckets would be cheaper but let N processes multiply the rate. Moderate to high risk of Google 429s |
| `google-provider:{coordination}:inflight:<policy>:<bucket>:<sha256>:binding` (string)                  | `2 x leaseMs` (20 to 60 s)                                          | Same policy, in-flight limit                                    | Pins the binding to the semaphore                                                      | Goes with the semaphore                                                                                                                                                                                              |
| `google-provider:{coordination}:inflight:...:leases` (sorted set, score = lease expiry)                | `2 x leaseMs`, each lease `leaseMs` (10 to 30 s)                    | Same policy, in-flight limit                                    | Cross-process semaphore capping concurrent Google calls                                | Postgres lease rows with expiry: simple, but poll and sweep cost, and crashed holders linger up to the lease                                                                                                         |

## Removal options and costs

1. **Keep the service as is (recommended for now).** About 650 lines stay (Redis client, store, scripts, entrypoint, verification). Cost: one more service to run and watch, plus the ACL and image pipeline.
2. **Move the app-Redis items in section C onto the provider Redis**, or delete the unused ACL prefixes. Tiny change; removes the mismatch. Decide which, it does not change behaviour for guests.
3. **Replace the small items with Postgres** (push reference, invalidation dedupe, refresh backoff, callback counter, refresh lock). Each is small and has a Postgres neighbour already. Removes no service on its own because the large items stay.
4. **Replace the large items** (review cursor store, quota and in-flight counters). The cursor store needs atomic multi-row swaps with tombstones. The quota and semaphore counters sit on every Google call; Postgres would add a locked write per call and contention across web and worker, with a real risk of exceeding Google's rate limits if done carelessly.
5. **Drop the service entirely** after options 3 and 4. Largest change: new tables and migrations, a sweep job for expired rows, new tests for each coordination rule, a second restore and rehearsal story, and the removal of the image, ACL, boot verification and Railway service. Gain: one fewer service and no restart-loses-state behaviour to design around.

Decision needed from the owner: option 1 or 2 now; options 3 to 5 only if running the extra service costs more than the migration.
