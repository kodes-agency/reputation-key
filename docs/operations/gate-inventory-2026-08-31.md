# Gate inventory — 2026-08-31

> **Remediation note (2026-09-03):** This inventory preserves the repository and
> platform observations made on 2026-08-31. The PR2 cutover deleted the duplicate
> root `CODEOWNERS`, the redundant pre-push hook, the local-stack CI smoke step,
> the unused `pnpm gate` runner, and the dead legal helpers; release signing now
> runs without the nonexistent protected environment; `triple` and `files` are
> guidance rather than matrix dimensions; and closed-beta Gate F requires 16
> evidence gates. The six-context branch-protection readback remains a post-merge
> operation and is not represented as completed here.

This document is the deliverable for issue #373: a complete, cited inventory of every automated gate
in this repository, classified by whether its demand genuinely depends on the size of the audience.
The rule applied throughout is the one `src/shared/release/gate-policy.ts:44-51` already machine-enforces:
a gate is **audience-dependent** only if its answer, or the requirement behind it, genuinely changes when
the only user is the owner operating on their own Google Business Profile; everything else is
**correctness**, because a bug is still a bug with an audience of one. The precedent being generalised is
`gateFApprovalRolesFor` (`src/shared/release/gate-f-evidence.ts:112`), which collapses six required
approval signatures to one at `closed-beta` by keying the requirement on posture _rather than deleting it_,
so it re-arms automatically when the posture widens. Two further verdicts are used and are deliberately
not collapsed into the binary: **both**, where one gate fuses a correctness arm and a ceremony arm that
should be split, and **unclear**, where the gate asks a question that sits on neither axis. Those rows are
the most useful output here and must not be flattened. All costs are measured from CI run 33387315575
(`gh api .../runs/33387315575/jobs`, event `pull_request`, head `docs/fact-map-verification-addendum`,
conclusion success) unless marked "local", and local figures are systematically 3-8x above CI and should
not be used for planning.

`GateClassification` (`gate-policy.ts:52`) admits only `'audience-dependent' | 'correctness'`, so the
18 rows below verdicted `both` or `unclear` cannot be registered as written — see Limitations.

## 5. Where the 17m44s actually goes

The `check` job ran 11:31:01 → 11:48:40 = **1059s**. It is a single serial chain, and the cost is not
distributed across the gates — it is four steps.

| Step                                                  | Cost     | Share     | Classification            |
| ----------------------------------------------------- | -------- | --------- | ------------------------- |
| 18 · **Test** (`check:coverage` + `test:integration`) | **629s** | 59.4%     | correctness               |
| 13 · **Typecheck** (3 projects + project coverage)    | **165s** | 15.6%     | correctness               |
| 14 · **Lint** (`lint:ci`, 13 sub-gates)               | **81s**  | 7.6%      | 11 correctness, 2 unclear |
| 12 · **Format check**                                 | **63s**  | 6.0%      | unclear                   |
| — subtotal                                            | **938s** | **88.6%** |                           |
| Fixed setup (steps 1-6)                               | 50s      | 4.7%      |                           |
| **All 24 remaining gates combined**                   | **71s**  | **6.7%**  |                           |

Within the 81s Lint step, extracted from the raw log timestamps: eslint + the three boundary/filename
checks = 68.0s; `check:zod-conformance` = 5.0s; `check:product-state-consistency` + `check-test-quality`
= 2.0s; `check:google-provider-fixtures` = 2.8s; `check:ai-contract-attestations` = 1.0s;
`check:ai-governance-artifacts` = 0.9s; `check:legal-registry` = 0.66s;
`check:runtime-environment-contract` = 0.5s. **All seven governance-sounding gates in that chain cost
~5.9 seconds combined.**

Three conclusions follow, and they reframe the whole exercise:

- **Posture-keying buys almost nothing on the clock.** Every audience-dependent gate outside the top four
  is worth 1-9s: artifact digest 3s, SBOM generate+upload 9s, bundle budget 1s, container images <1s.
  Removing all of them saves ~13s of 1059s — 1.2%. Of the four expensive steps, one is pure correctness
  (Typecheck), one is dominated by correctness (Test), one is a mostly-correctness aggregate (Lint), and
  exactly one is not correctness (Format check, 63s) — and _that_ one cannot be honestly posture-keyed
  either, because its trigger is contributor count, not audience.
- **`docker` is not the bottleneck.** It has no `needs:` (`ci.yml:291-293`), ran 11:30:58 → 11:39:52 =
  534s, and finished eight minutes inside the `check` ceiling. Deleting the entire job — ten builds, the
  smoke step, ten SBOMs, ten scans — would shorten the run by **exactly zero seconds**. Its internal split
  is grype 221s / builds 176s / SBOM 101s / smoke 15s. If the SBOM steps are dropped, do it because a solo
  closed beta has no SBOM consumer, never because it saves time.
- **The only real lever is parallelism.** `test:integration` runs `fileParallelism: false`,
  `maxWorkers: 1` (`vitest.config.ts:141-142`) inside the serial chain; unit is `maxWorkers: 4` (`:114`).
  Hoisting integration into its own job is the single highest-value change available, and `docker` at 534s
  already proves there is idle parallel capacity beneath the ceiling. Second: `eslint .` runs without
  `--cache` (`package.json:28`) and declares no type-aware linting, so its 68s is raw file volume.

One coupling to price in: **nothing in the `docker` slice can be changed by editing `ci.yml` alone.**
`check-container-image-policy.ts:183-238` (run as `pnpm check:container-images` in the _critical-path_
`check` job) fails if any classified image lacks a build line, a smoke mention, an `SBOM …` step, or a
`Vulnerability scan …` step; and `gate-wiring.test.ts:111-114` asserts the grype-pair count equals the
image count. Dropping one SBOM step is a three-file change. That coupling is a feature — it is what stops
a gate quietly vanishing — but it is real.

Two proposals were rejected as _flips_ while being accepted as _facts_, and that distinction is the useful
one: in both cases the correction's evidence was correct and load-bearing (AGPL/SSPL are excluded only by
absence from a closed allow-list; `release-images.yml` has never run, so the SBOM fallback is fictional),
but the right response was to mark the gate `keptArmedByChoice` rather than to relabel it. The registry
already has that mechanism (`gate-policy.ts:180-190`), and using it is more honest than moving a gate to
`correctness` so that `validateGatePolicy` will force it to stay on.

## 7. Limitations

- **The brief's premise "there are no third-party data subjects today" is false for this system, and
  several classifications turn on it.** Verified: `CORE_CAPABILITIES` (`src/shared/auth/beta-capabilities.ts:82-93`)
  arms `property.connect_gbp`, `review.use`, `inbox.use` and `property.publish_reply` by default in the
  closed beta, and `Review` (`src/contexts/review/domain/types.ts:30-41`) holds `reviewerName`,
  `reviewerProfilePhotoUrl` and `text` — "the guest's own words". Google reviewers are third parties who
  never used, saw, or consented to this product, and they exist on day one at an audience of exactly one
  operator. Any mechanical application of "no third-party data subjects" across the inventory produces
  wrong answers at `portal_privacy`, `observability_content_inspection`, and the counsel checklist.
- **One product fact could not be determined from the repo and decides the `compatibility` gate's balance:
  whether real guests scan portals during the closed beta.** The code says `/p/{token}` is third-party
  facing by design; the brief says there are no third-party data subjects. That contradiction should be
  resolved by the owner, not inferred.
- **The registry cannot express 18 of these rows.** `GateClassification` (`gate-policy.ts:52`) admits only
  two values, and `validateGatePolicy:229-234` forces correctness → `armedFrom: closed-beta`. The `both`
  and `unclear` rows must either widen the union, split into two registry entries each (the better outcome
  for `check:container-images`, `check:technology-stack` and `deployed_critical_journeys`, where the
  ceremony arm is the only thing worth scoping), or be registered by dominant arm with the caveat in the
  rationale.
- **No gate was made to fail deliberately, except two.** "Can it fail" claims are read from exit paths in
  source, not demonstrated — the exceptions are `check:legal-registry` (digest tampering and an
  unregistered document both produced exit 1) and the live platform readbacks.
- **Two costs are unmeasured.** `check:schema-drift` needs a fully migrated Postgres, unavailable here; and
  the `secrets` job's merge-path cost (`--log-opts=--all`) was not exercised by the cited run — it is
  documented at 8m25s for 1960 commits, roughly 30x the PR-path 17s.
- **The sub-second gates inside the Lint step were attributed from log banner timestamps, not from
  isolated runs.** Splitting `check:google-provider-fixtures` into its two halves would require editing the
  script.
- **Three calendar time bombs are live and will fail with zero code change:**
  `security/technology-stack.json` `nextReviewBy: 2026-11-26`; all four license exceptions expiring
  2026-10-31; and every `.grype.yaml` entry expiring 2026-10-31 — the last with **no automated expiry at
  all**, because "the gate cannot read comments". That is an audience-invariant hole in the strongest gate
  in the docker slice.
- **Stale governed documentation, which is itself a defect.** `security-ci-policy.md:170-189` states in
  bold that main has no branch protection, with a 404 transcript dated 2026-08-21; a live readback today
  returns 200 with five required contexts — `check`, `docker`, `e2e`, `secrets`, `audit` — and, contrary
  to an earlier draft of this document, **no** review requirement of any kind. `.github/CODEOWNERS:2-3`, `/CODEOWNERS:3`
  and `ci.yml:861` repeat the false claim, and `ci.yml:861` is the stated justification for moving
  beta-acceptance off the PR path. Separately, `entry-point-catalogue.ts:5555` describes `check:coverage`
  as "MAIN ONLY" when `ci.yml:172` runs it unconditionally — and the catalogue is itself gated content.
- **Two orphaned verifier scripts are a coverage gap, not over-gating.**
  `scripts/verify-ai-execution-admission-bundle.mjs` and `scripts/verify-ai-egress-gateway-bundle.mjs`
  exist but appear in neither `package.json` nor anything under `.github/`, while the Google equivalents
  are invoked. Whether they are dead or merely unwired was not determined.
