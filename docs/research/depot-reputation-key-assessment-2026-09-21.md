# Depot.dev for Reputation Key: workload assessment and recommendation

**Date:** 2026-09-21. **Decision:** run a bounded experiment; do not migrate the full CI pipeline yet. Read the [companion Depot product research](depot-dev-2026-09-21.md) for current product, pricing, security, and compatibility sources. Depot's published speed multipliers are vendor claims. No Depot build or runner was executed for this assessment.

## Executive assessment

Depot is a credible fit for the Docker-heavy portions of this repository, especially the four E2E shards that each build a Compose stack on an ephemeral GitHub runner. Its remote BuildKit cache could avoid repeated dependency and image layers, and its runners might shorten image loading, browser setup, and tests. The benefit is **unproven** until measured from workflow start to a usable image or completed check. The fast local HMR loop (`pnpm dev` / `pnpm local:up`) will see little direct benefit: the web and worker already run on the host, and Depot accelerates container builds rather than Vite, TypeScript, Vitest, or Playwright by itself.

This is a **public** GitHub repository. Standard GitHub-hosted Actions runners are free for public repositories, so Depot adds a bill rather than replacing a current compute bill. Its value must be shorter feedback, more predictable builds, or developer time saved. [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions); repository visibility checked with `gh repo view kodes-agency/reputation-key --json isPrivate` on 2026-09-21.

## Measured baseline

The main [CI workflow](../../.github/workflows/ci.yml) has four unit shards, integration, static checks, source artifacts, two grouped image-build jobs, four E2E shards, Storybook, secrets, and aggregation jobs running mostly in parallel. The image groups build five classified descriptors. Their Buildx invocations already import and export separate `type=gha` caches per image. The E2E shards start a [Compose stack](../../compose.local.yml) via [stack-services.sh](../../scripts/e2e/stack-services.sh), which calls `docker compose ... up --build` for support services; they then build and start the production web image. This is repeated on each ephemeral shard without an explicit shared Buildx cache for those Compose builds. The test job also installs Chromium, Firefox and WebKit with an `actions/cache` browser cache.

Five recent successful [workflow runs](https://github.com/kodes-agency/reputation-key/actions/workflows/ci.yml) showed:

For [run 35360668838](https://github.com/kodes-agency/reputation-key/actions/runs/35360668838), the worker-tools image group spent 167 seconds in its grouped build, 38 seconds generating image SBOMs, and 23 seconds staging images. **Critical-path implication:** in that run, the last E2E aggregate finished at 15:14:42 UTC and the final Docker aggregate finished at 15:15:10 UTC. Even making the image-group build instantaneous would have saved at most about **29 seconds** of workflow elapsed time unless E2E also changed. In several other runs E2E was already last. Optimizing the production image group alone may save its runner-minutes but little merge wait time.

Activity is high: the GitHub workflow API reported **786 CI runs from 2026-09-01 through 2026-09-20**, comprising 445 successes, 275 failures, and 66 cancellations. A representative 44 runner-minutes multiplied by 445 successful runs is about 19,600 minutes _before_ failed runs or other workflows. This is only a planning illustration: actual billed usage requires per-job durations across all runs and will change if jobs finish faster.

The GitHub Actions cache API reported **65 active caches totaling 9.7 GB** on 2026-09-21. Depot's 25-GB Developer allowance covers cache **and registry** storage, while its Docker build cache has a separate project policy; do not infer Depot's bill from GitHub's current cache total. ## Where Depot could help

| Workload                              | Current constraint                                                                                                              | Expected Depot effect                                                                                                                           | Confidence                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| E2E Compose images on four shards     | Repeated `--build` on ephemeral runners, production image loaded locally for tests                                              | Persistent remote Docker layers could shorten repeat builds; `--load` sends images back to each runner and may offset gains                     | **Medium opportunity, unmeasured result**                     |
| Two CI image groups                   | Five builds, separate GHA cache scopes, same Dockerfile used for web and worker; grouped build takes 91–167s in the sampled run | Faster layer access and more CPU could reduce build step; current GHA cache already captures many layers, and SBOM/scan/stage work remains      | **Medium build-step opportunity, low total-run upside alone** |
| Non-Docker checks                     | Static, Vitest, Playwright, and browser setup use 2-core GitHub runners                                                         | Depot runners offer faster storage/cache and larger sizes; 2-core speedup must be measured, while larger sizes consume allowances faster        | **Unknown**                                                   |
| Local HMR development                 | Vite and worker run on host; Compose provides services                                                                          | Remote builders can help initial/repeated support-image builds, but do not accelerate source edits, HMR, typecheck, or tests directly           | **Low for the inner loop**                                    |
| Local production-image and E2E builds | Docker may consume laptop CPU; this host is Arm64                                                                               | Remote builders can share cache and free local resources, but pulling large images back may dominate; build target architecture must be checked | **Potentially useful for occasional acceptance work**         |

The production [Dockerfile](../../Dockerfile) pins its Node base, installs dependencies from a frozen lockfile, and then copies the source. This gives Depot reusable dependency layers, but the `SOURCE_REVISION` build argument is declared before the application build; it changes on each commit, so the expensive `pnpm build` step is not automatically reusable across revisions. Persistent remote cache is therefore most likely to help unchanged base/dependency layers and repeated builds of the **same** commit, not remove all application compilation. Depot's Docker guidance is [here](https://depot.dev/docs/container-builds/overview).

## Costs and migration constraints

The [published Depot plans](https://depot.dev/pricing) are $20/month for one Developer user or $200/month for a multi-user Startup team. Each has separate allowances for container-build minutes, GitHub Actions runner minutes, Depot CI minutes, and shared cache/registry storage. Developer includes 500 build minutes, 2,000 base runner minutes, and 25 GB; Startup includes 5,000 build minutes, 20,000 base runner minutes, and 250 GB. Base runner overage is $0.006/minute; default container-build overage is $0.04/minute; storage overage is $0.20/GB-month. Larger sizes multiply included-minute consumption. At an illustrative **20,000 base runner-minutes in one month**, runner-only pricing is about **$128 on Developer** (one user) or **$200 on Startup**, before container builds or storage. This is a scenario, not an invoice or a forecast. The public-repo GitHub baseline is $0 for standard runners. [Depot runner pricing](https://depot.dev/docs/github-actions/overview); [GitHub public-repo billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

The least invasive product is **Depot Container Builds inside existing GitHub Actions**. An isolated workflow can use short-lived GitHub OIDC authentication and keep GitHub's job logs, checks, and release orchestration. It must remove the current `--cache-from/to type=gha` flags for that build: Depot documents conflicts with those flags because its builder already persists layers. The existing [container-image policy checker](../../scripts/ci/check-container-image-policy.ts) explicitly requires `docker buildx build`, `--load`, and those cache flags, so a production switch requires a deliberate policy update that preserves image classification, smoke, SBOM, Grype, and release digest checks. [Depot GitHub Actions integration](https://depot.dev/docs/container-builds/integrations/github-actions); [cache troubleshooting](https://depot.dev/docs/container-builds/troubleshooting).

**Depot GitHub Actions runners** keep the workflow on GitHub, but redirect `actions/cache` requests to Depot's backend. Depot cache entries are repository-scoped and **not branch-isolated**. This repository runs public PRs and Dependabot updates, so cache keys and write access need a trust review before moving required jobs. A runner-only pilot should use a non-deploy job and compare actual GitHub job creation-to-completion time, including runner allocation. [Depot cache integration](https://depot.dev/docs/cache/integrations/github-actions); [runner overview](https://depot.dev/docs/github-actions/overview).

**Depot CI** is a separate orchestration migration and is not needed to test the speed hypothesis. Current compatibility docs list no fork-originated PR workflows, no GitHub deployment environments, and no GHCR authentication with its GitHub App `GITHUB_TOKEN`. This repository's PR checks and main-branch promotion to GHCR make those material gaps. A copied workflow can run twice unless GitHub triggers are explicitly retired. Branch protection, release evidence, GitHub token identity, and any external OIDC trust would need separate validation. [Depot CI compatibility](https://depot.dev/docs/ci/compatibility); [Depot CI quickstart](https://depot.dev/docs/ci/quickstart).

One existing secret path deserves attention before **remote web builds**: CI passes `SENTRY_AUTH_TOKEN` into the Dockerfile as a `--build-arg`. Docker explicitly advises using BuildKit secret mounts instead of `ARG` for credentials because build arguments may appear in history or provenance. The source-map upload needs to keep working, but this should be corrected before granting a remote builder that credential. A first pilot can build the provider-sandbox image, which does not need the Sentry token. This is an existing build concern, not evidence of a Depot vulnerability. [Docker build secret guidance](https://docs.docker.com/build/building/variables/).

## Recommended experiment and decision rule

1. **Establish a reproducible baseline.** Record at least ten normal, cache-warm successful PR or main runs, plus one cold-cache build. Capture workflow wall time, each job/step time, E2E stack-build time, image bytes loaded, cache hit/miss, and effective cost. Keep the existing GitHub required checks as the control.
2. **Run an isolated Container Builds pilot.** Start with the support-image build used by E2E, without publish credentials or production secrets. Use a separate, non-required workflow or local test so branch protection and release promotion stay intact. Compare the same commit and architecture with the GitHub Buildx control using `--load`; measure until the image is actually present in Docker. Then test one E2E shard end-to-end. Check fork and Dependabot behavior before expanding.
3. **If the first experiment wins, test one runner job.** A non-deploy E2E or integration shard is more informative than a tiny unit shard. Measure startup, cache transfer, test duration, flake rate, and billed normalized minutes on the base and one larger size.
4. **Adopt only for an observed win.** A useful threshold is at least **one minute off the median total CI critical path** or a repeatable **20% reduction in the targeted E2E job**, with no loss of required gates, PR coverage, provenance, or release semantics. This is a proposed decision threshold, not a vendor guarantee. Calculate dollars per month from actual Depot usage and the number of developers blocked by CI. If only the Docker group speeds up while E2E stays last, keep the existing setup.

**My opinion:** a full move to Depot CI is premature. Depot Container Builds are worth a narrow benchmark because this repository does repeated Compose builds on four shards. Depot runners are worth a second benchmark if the E2E job or package/browser caches remain the long pole. The public GitHub baseline and already-short 5–8 minute successful runs make a large, paid migration hard to justify without a measured critical-path improvement.
