# Depot.dev: external product research

Researched 2026-09-21 from Depot's current first-party documentation and pricing. This note describes the vendor and its constraints; repository workload analysis and an adoption decision belong in the companion project assessment. Depot's speed multipliers are **vendor claims, not measured results for Reputation Key**.

## What can be adopted independently

## Container-build mechanics and developer workflow

`depot build` uploads the Docker build context to a remote BuildKit builder. The output remains in the remote project cache unless requested with `--load`, `--push`, or equivalent output settings. `depot bake` can build Docker Compose or Bake targets in parallel; `depot bake -f docker-compose.yml --load` returns service images to a local Docker daemon. Local users authenticate with `depot login` and can select a project via `depot init` (which writes `depot.json`) or `--project`. `depot configure-docker` can route ordinary `docker build` / `docker compose build` through Depot. Downloading a large image back to a laptop can erase part of the remote-build gain, so measure **command start to image ready for use**, not merely BuildKit execution time. Sources: [container-build overview](https://depot.dev/docs/container-builds/overview), [local development](https://depot.dev/docs/container-builds/how-to-guides/local-development), [Docker Compose guide](https://depot.dev/docs/container-builds/how-to-guides/docker-compose).

The cache namespace is a Depot project, shared by all authorized builders in that project, including team members and CI. Its Docker-layer policy defaults to a 50-GB project cache, with configurable 7/14/30-day retention and storage up to 1,000 GB. BuildKit can retain parent layers beyond the nominal limit because recent layers depend on them. Depot says fork-PR builds for open-source repositories are isolated from the project's persistent cache. Cache hits still depend on Dockerfile structure: source copied before dependency installation, changing build arguments, or changing inputs can invalidate expensive layers. Sources: [container-build cache and isolation](https://depot.dev/docs/container-builds/overview), [Docker build optimization guide](https://depot.dev/resources/guides/how-can-i-speed-up-docker-builds-in-github-actions).

In existing GitHub Actions, Depot recommends its `setup-action` plus `build-push-action` or `bake-action`. GitHub OIDC can authenticate to a project with `contents: read` and `id-token: write`, avoiding a static Depot token. Depot warns against exporting the same build to GitHub Actions cache with `cache-from/to: type=gha`: its persistent layer cache is already active and that configuration can fail. A remote image pushed directly to a registry avoids downloading it through the CI runner; integration tests that need the image locally require `load` or a pull and should be timed end-to-end. Sources: [GitHub Actions container-build integration](https://depot.dev/docs/container-builds/integrations/github-actions), [build troubleshooting](https://depot.dev/docs/container-builds/troubleshooting), [container-build overview](https://depot.dev/docs/container-builds/overview).

## Runner and CI distinctions

Depot GitHub Actions runners use fresh EC2 instances registered in the GitHub organization's default runner group for each job and terminated afterward. Linux base runners have 2 CPUs, 8 GB RAM and a 100-GB disk; larger x86 and Arm labels are available. Depot says runner images generally follow GitHub's but can lag. Its standard `actions/cache` integration changes the storage backend automatically, with entries scoped to a repository **but not isolated by branch**; cache keys therefore need to encode trust and compatibility where relevant. Runner startup is not zero; Depot documents a typical 10–45-second allocation interval, which should be included in wall-time comparisons. Sources: [runner overview](https://depot.dev/docs/github-actions/overview), [runner types](https://depot.dev/docs/github-actions/runner-types), [runner troubleshooting](https://depot.dev/docs/github-actions/troubleshooting), [cache integration](https://depot.dev/docs/cache/integrations/github-actions).

Depot CI is a different execution engine, not just a runner label. It reports GitHub checks but keeps workflow logs and control in Depot. It supports GitHub Actions YAML, jobs with service containers, matrices, reusable workflows within the repository, and common JavaScript/composite/Docker actions. Its published limits include unsupported GitHub deployment environments, reusable workflows from **other** repositories, fork-originated PR workflows, GitHub-only event types, and macOS/Windows sandboxes. Its `GITHUB_TOKEN` is a GitHub App token: the docs say it cannot authenticate to GitHub Packages/GHCR, so such jobs need a different registry or a separately managed PAT. Cloud-provider OIDC must trust `https://identity.depot.dev` and Depot's subject format instead of GitHub's OIDC issuer. Sources: [Depot CI overview](https://depot.dev/docs/ci/overview), [compatibility matrix](https://depot.dev/docs/ci/compatibility), [GitHub checks](https://depot.dev/docs/ci/observability/github-checks), [OIDC guide](https://depot.dev/docs/ci/oidc).

Depot's CI migration copies workflows into `.depot/`; the `.github/` copies continue to run. Its quickstart warns that deploys or other external effects can run twice after activation. The optional secret import creates a temporary GitHub Actions workflow that reads existing secrets and sends them to Depot CI; review this operation before using it. Depot CI also permits local `depot ci run` against uncommitted changes. **Documentation inconsistency:** the current Depot CI overview and an official migration walkthrough describe `schedule` support, while the CLI migration reference lists `schedule` among triggers removed as unsupported. Verify the installed CLI's migration output and a real scheduled run before depending on it. Sources: [CI quickstart](https://depot.dev/docs/ci/quickstart), [CI overview](https://depot.dev/docs/ci/overview), [CLI reference](https://depot.dev/docs/cli/reference/depot-ci), [official migration walkthrough](https://depot.dev/blog/migrate-to-depot-ci).

## Pricing and cost model (published rates, not a quote)

The Developer plan is $20/month for one user; Startup is $200/month with unlimited users; Business has custom pricing. The allowances are **separate pools**, not a single 4,500/45,000-minute bucket. The published Developer / Startup monthly allowances are 500 / 5,000 default-size container-build minutes, 2,000 / 20,000 base Linux GitHub-runner minutes, 2,000 / 20,000 base 2-vCPU Depot CI minutes, and 25 / 250 GB of cache and registry storage. Extra default container-build time is $0.04/min; extra base Linux runner time $0.006/min; extra base Depot CI time $0.0001/sec (= $0.006/min); extra cache storage $0.20/GB/month. Larger machines multiply allowance consumption and overage rate: 32-vCPU container builds are 2×, 4-vCPU Linux runners 2×, and 4-vCPU Depot CI sandboxes 2×. Usage is measured by the second with no per-job one-minute minimum; included minutes are not hard caps unless an organization sets usage caps. Sources: [pricing](https://depot.dev/pricing), [container-build pricing](https://depot.dev/docs/container-builds/overview), [runner sizes and multipliers](https://depot.dev/docs/github-actions/runner-types), [Depot CI sandbox pricing](https://depot.dev/docs/ci/overview), [cache pricing](https://depot.dev/docs/cache/overview).

An estimate should calculate each pool separately: `monthly fee + max(0, build-minutes − included-build-minutes) × build-rate + max(0, runner-minutes − included-runner-minutes) × runner-rate + max(0, CI-minutes − included-CI-minutes) × CI-rate + storage overage`. Normalize minutes by size multipliers, and count concurrent jobs separately. Compare this against the **actual GitHub bill** and the value of saved engineer wait time; a faster job may lower compute minutes, while new parallelism, larger machines, or a second CI run during migration may raise total spend. This formula is derived from the published plan tables; the cost outcome must be measured for this repository. Sources: [pricing](https://depot.dev/pricing), [container-build pricing](https://depot.dev/docs/container-builds/overview), [runner pricing](https://depot.dev/docs/github-actions/overview), [CI pricing](https://depot.dev/docs/ci/overview).

## Security and operational diligence

Depot says builder/cache resources are assigned per organization and project, build traffic uses TLS and build-specific mTLS certificates, cache volumes are encrypted at rest, and the service has SOC 2 Type 2 compliance. CI secrets are encrypted with an organization-specific KMS data key and AES-256-GCM, and only organization owners can manage them. These are vendor-stated controls; the report and contractual terms need direct review for a production trust decision. Depot's own security guide stresses that anyone allowed to build in a project can potentially read or alter its cache. Scope OIDC trust relationships to the correct repository/ref and avoid sharing a build project between less-trusted and production workloads. Sources: [security documentation](https://depot.dev/docs/security), [security page](https://depot.dev/security), [CLI authentication](https://depot.dev/docs/cli/authentication).

Depot runs US and EU cloud regions, with EU residence selected per project; Depot Managed, a Business-plan option, can place build compute and cache data in the customer's AWS account while Depot still operates the CLI, web application and API. Regular Depot runners receive changing AWS public egress IPs, so a service requiring IP allowlisting needs VPN, VPC or a separately arranged static-IP option. Depot runners also require a GitHub organization repository and an installed GitHub App. These dependencies should be verified against any private package sources, deployment targets and data-residency requirements. Sources: [security regions](https://depot.dev/docs/security), [Depot Managed](https://depot.dev/docs/managed/overview), [private-resource access](https://depot.dev/docs/github-actions/how-to-guides/access-private-resources), [runner quickstart](https://depot.dev/docs/github-actions/quickstart).

## Product-research conclusion

The smallest credible pilot is one existing Docker image build on Depot Container Builds while leaving GitHub Actions intact. It tests the persistent-cache benefit, remote-context transfer, image delivery, and actual cost without moving the CI control plane. A second pilot can move one non-deploy job to a Depot GitHub Actions runner to measure package-cache and filesystem gains. Depot CI offers stronger local and debugging features, but its compatibility and identity changes make it a later, separate decision. This is an **inference from the product boundaries and limits above**, not a measured speed recommendation for Reputation Key. Sources: [container-build overview](https://depot.dev/docs/container-builds/overview), [runner overview](https://depot.dev/docs/github-actions/overview), [CI compatibility](https://depot.dev/docs/ci/compatibility).
