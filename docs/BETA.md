# RepKey closed beta — the contract

Authority for the closed beta. If this page and a document disagree, this page wins; if this page and the code disagree, that is a bug in one of them — say which. Rules here name the test or lint path that enforces them. A rule with no enforcement is marked **UNENFORCED** and is a liability, not a rule.

## 1. What the beta is

- Organizations and Properties are operator-provisioned; no count is fixed. Self-service is off — `identity.register` and `organization.create` are `beta_disabled`, so growth is an operator action, not a signup. Operators create each later Organization from the operator console (`/operator`, ADR 0065), which invites its first AccountAdmin.
- A user holds exactly one active Better Auth Organization membership, and an invitation never creates a second one. An invitation, or the renewal of one, is refused with the Identity error `organization_conflict` (HTTP 409) when its address already belongs to another Organization or holds an unexpired pending invitation from one, and accepting an invitation is refused with the same code when the account has meanwhile joined another Organization, checked under a per-user lock in the acceptance transaction (`assertAddressHasNoMembership`, `lapsedCompetitorIds` and `assertRenewalHasNoCompetitor` in `invitation-store-rules.ts`, `checkSingleOrganizationMembership` in `identity-command-store.ts`; `invitation-store-rules.test.ts`, `identity-command-store.test.ts`). `organization_membership_conflict` is a different refusal, an auth error also answered 409, and no invitation path raises it: the tenant resolver raises it for a session whose active Organization is not the account's one membership (the account has none, another, or more than one), `setActiveOrganization` raises it for a switch to such an Organization, and the account then waits for support (`src/shared/auth/tenant-resolver.ts`, `tenant-resolver.test.ts`).
- One deployment serves everywhere: Railway `us-west2`, object bucket `sjc`, every supported country routed to it. There is no per-region deployment and no customer-visible region choice. Physical placement, country, and logical routing are distinct facts and are not encoded in one mutable Property field. Country and timezone remain editable business facts and do not move existing data.
- No contractual uptime SLA, service credits, or 24/7 support. Support hours, service levels, warranties, disclaimers, and liability terms are not agreed; the accepted Closed Beta Participation Agreement version 2.1 creates none of them (`docs/legal/internal-beta-agreement.md:226-229`).
- No MFA, and the product no longer says otherwise. The security settings page used to ship a "Two-factor authentication … Coming soon" card that did nothing while no TOTP existed anywhere in `src/`; WP1.7 deleted the card rather than implementing the feature.

Written commitments to Google (2026-07-14 response) and to users. Not changeable unilaterally; they outrank everything below.

Naming the import routes in that branch is a migration that restates the function (not made). `CAPABILITY_ROUTES` in `execution-admission.ts` belongs to the in-memory admission the control tests use; production admits through `admission-service.ts`, whose permit carries no capability, so that table is not a control. - **Raw Google content is served at most 30 days from fetch; deleting it at that age is UNENFORCED** — `rawContentTtlMs` is 30 d, refresh is due at 25 d, and the expiry is stamped from the last successful Google fetch and never reset by publication (`createGoogleSourceContentPolicy` and `contentExpiresAtFromFetch` in `source-content-policy.ts`). Serving reads withhold a row once its expiry has passed, and a row that has none (`isContentEligibleForRead`; `eligible-reads.test.ts`). **UNENFORCED** for what is stored: nothing deletes on the expiry. The two jobs that would, `purge-expired-reviews` and `expire-review-provider-source`, have no schedule and delete nothing while the destructive Review lifecycle is quarantined: the first only reports, the second drains its payload and answers `quarantined` (`schedule: 'none'` and `registration: 'quarantined'` on both rows of `event-job-catalogue.ts`; `purge-expired-reviews.job.test.ts`, `review-lifecycle-safety.test.ts`, `src/shared/jobs/readiness.test.ts`), and the retention registry lists the class with no executing rule (`google.source_content` in `retention-registry.ts`). ## 3. Product contract

- **Accounts.** An account is created only by consuming a valid email-bound invitation; there is no self-service registration. The one exception is the first AccountAdmin of an empty environment, created by the operator command `ops:bootstrap-owner`, which refuses once any account or Organization exists. Every later Organization's first AccountAdmin is invited from the operator console. Interactive roles are `AccountAdmin` and `PropertyManager`; runtime custom roles are off. A Staff Participant is a manager-maintained profile with no login. Consuming the invitation verifies the email address and signs the member in; no separate verification email is sent. An invitation cannot be consumed while its Organization is suspended, `identity.invite` is switched off or restore mode is isolated: it is refused before anything is written and stays pending (`invitation-capability-gate.integration.test.ts`). Resend renews an invitation's expiry. A password reset also verifies the address. Only AccountAdmins invite, cancel or resend invitations, change roles, edit a PropertyManager's Properties, and edit Organization settings; an invitation defaults to PropertyManager. No MFA; the only step-up is the operator console's 30-minute recent-sign-in rule. No billing surface.
- **Properties.** The product serves service venues such as hotels, restaurants, barbers and salons (owner decision: no place types), so it has no venue type: nothing asks for one, shows one, filters by one or refuses a venue for lacking one. A Property does hold one Google-supplied fact about its kind of business, the primary category Google reports for its location (for example "Hotel" or "Italian restaurant"; `properties.google_primary_category`), read at import and again at relink, with no background refresh between them (`src/contexts/property/CONTEXT.md`, invariant 15). It is a hint and nothing else: it chooses which vocabulary hints a review analysis is steered with (`review-vocabulary-hints.ts`), no screen shows it, no query filters or ranks by it, nothing is gated on it, and a change to it moves no profile version, source epoch or AI epoch and re-analyses nothing. A Property whose category is empty, or is not one the hint catalogue lists, gets the generic hints. The provider identity scrub, which runs when a Google connection is removed, clears it with the other Google-supplied descriptors. Geographic availability is not localization — the manager app and operational email are English. Editing a Property's country or timezone changes business facts only; it moves no data.
- **Portal.** A review gateway first, link tree second, with mandatory first-party Portal-scoped analytics that cannot be declined. The page leads with the private 1–5 rating card, which stays first and dominant; on the Immersive Hub (publication snapshot schema v3) the Linktree is visible from arrival and in every state after it (owner decision 2026-09-30, ADR 0044 amendment 2026-10-01), so a tap on it before any rating is navigation only and never a Qualified Link Action; v1 and v2 snapshots keep the legacy page, where the destinations follow the rating, until the Portal is republished. The visitor gives a private 1–5 rating first; the Google Review Action then stays available to everyone and records only that the visitor selected the verified destination — RepKey cannot observe whether a review was written.
- At or below the Private Feedback Threshold (inclusive, valid `1..5`, default `3`) the visitor is additionally offered private feedback; `0` and `6` are rejected, so private feedback cannot be disabled and Google is never blocked (`guest-response-lifecycle.test.ts`).
- A stale, `awaiting_refresh` or `unavailable` Google destination degrades the Portal to rating plus private feedback; a stale URI is never rendered.
- The creator is immutable provenance and, when eligible, the default Portal Responsible Manager; only active assigned Responsible Managers get Portal notifications, with AccountAdmin as fallback. A Portal belongs to zero or one Portal Group. Removal is recoverable Archive; restoration returns the Portal to Disabled until a deliberate republish.
- Contact collection is built but blocked, with no surface and no activation path (`portal.guest_contact` is `safety_blocked`). Its design is explicit "Please contact me" consent, off by default, never required, masked until an audited reveal, excluded from analytics and routine export, purged exactly 30 days after submission (DB check `expires_at = submitted_at + '720:00:00'`). RepKey does not message guests.
- **Guest retention as the sweep executes it** — private feedback 90 d, contacts 30 d, network-pressure exactly 7 d, abuse pseudonyms 7 d, de-identified facts 24 months, session pseudonyms **1 day** (`retention-sweep.job.ts:78-148`). The program document says 7 days for session pseudonyms; the code is 1 day and the code is right. The 1 day covers the session's own records, not every copy of its identifier: the binding is deleted once its expiry has passed (24 hours after the guest's last rating or private feedback) and the `session_id` on `scan_events`, `ratings` and `feedback` is cleared 1 day after the row was created, but each Qualified Scan and each first destination selection also writes the identifier into the key and payload of an idempotency receipt (scopes `guest_qualified_scan` and `guest_destination_action`, `guest-observation-store.ts:95,140-151,221-252`). A receipt stops deciding anything when the session ends, yet only the shared `idempotency_receipts` rule removes it by age, after **30 days** (`retention-sweep.job.ts:177-183`); an Organization purge removes it sooner, and so would a Property erase, which is `beta_disabled` today (§8). The sweep runs once a day, so a row can outlast its horizon by a day, or longer when a run fails or stops at its per-run cap (100 batches a rule, `execute-retention-rule.ts`). The Privacy Notice has stated both horizons since version 2.1 (§2). The 24 months execute for three Guest stores: the rating fact on its stamped `retention_deadline`, and the counted visit (`guest_qualified_scans`) and the visit record (`scan_events`) 24 UTC calendar months after the visit (a visit made on 28 February waits one day more when the run two years later falls on 29 February, `retention-cutoff.ts`). Deleting those rows does not remove the fact. Reporting records a `metric_readings` row from every visit, rating, private feedback and destination selection (metric keys `portal.scan`, `portal.qualified_scan`, `portal.rating`, `portal.rating_count`, `portal.rating_average`, `portal.feedback`, `portal.review_link_click`), holding the Portal, the instant, the source event, the value and any staff attribution, and no rule deletes one, so on the day the Guest row goes the same visit or rating is still stored there. **UNENFORCED** for those readings, for their corrections and for v2 AI derivatives, which the accepted notice also puts at 24 months (§2): a reading the Portal's lifetime aggregate is built from (`portal.qualified_scan`, `portal.rating`, `portal.feedback`, `portal.review_link_click`) must not be deleted before that aggregate is sealed through its day, and nothing runs that seal; the other three feed no aggregate and have no rule either; a correction goes only with the reading it corrects; a v2 AI derivative past its 24 months is withheld from reads and stays stored (`retention-registry-guest-facts.ts` and `retention-registry.ts`, horizon `accepted_unexecuted`; `retention-registry.test.ts` pins the list and that it names every Guest-derived metric key). A v3 AI derivative does not wait: the sweep first deletes a Review Analysis v3 analysis at the `expires_at` it stamped (completion plus 730 days), taking its mentions, their sentence numbers, a manager's corrections beside those mentions, its aggregate contribution and that contribution's mentions in the same statement by cascade; it then deletes an expired Property issue group once no contribution mention references it, taking its members and merged redirects by cascade; and it deletes the daily star counts of a Property 24 UTC calendar months after the day they count (`ai_review_analyses.v3_expired`, `ai_property_issue_groups.expired` and `ai_property_review_population_daily.expired` in `retention-sweep.job.ts`, `retention-registry-ai.ts`; the v3 retention tests prove the paths from the schema and against PostgreSQL). Nothing selects a v3 analysis yet, so those rules delete nothing until it is activated. Enforced by `qualified-scan.integration.test.ts` (both receipts keep the identifier after the one-day sweep and go at 30 days; the counted visit and the visit record go at 24 months), `guest-observation-store.test.ts` (the 30-day sweep) and `retention-sweep-guest-session-disclosure.test.ts` (this line, the notice and the data inventory state the sweep's figures).
- **Google and Review.** A Google Connection is Organization-owned; AccountAdmins connect, reauthorize and disconnect. "Select all eligible locations" imports through resumable batches of at most 100, which is a worker bound and never a product selection cap. Pub/Sub is the fast path, targeted fetch handles a notification, adaptive polling reconciles, manual sync recovers. A quiet healthy Property is polled about four times a day, which is an interval and not a worst case: on the default 15-minute base its next poll is dated six hours ahead, the cap (`DISCOVERY_MAX_INTERVAL_MS`), and runs at the first 15-minute discovery sweep at or after that instant, so with Pub/Sub dark a new review on it is found up to about six and a quarter hours after it was posted, plus the sync itself. A discovery look skips the full snapshot while the Property's last completed reconciliation is under six hours old (ADR 0055, note of 2026-10-21): a busy Property is read in full about four times a day too, not every 15 to 60 minutes, and a push no longer brings a full read forward. This holds only with Pub/Sub configured; with it dark every look stays full on the ladder above, and `REVIEW_DISCOVERY_SKIP_RECENTLY_RECONCILED=false` turns the skip off. A review whose push is missed is found at the next reconciliation, up to about six hours later. It is later still when one sweep finds more than 2,000 Properties due, its budget for a run, and when the operator sets `REVIEW_DISCOVERY_INTERVAL_MINUTES` above 360: no Property is polled more often than that base interval, which then outranks the six-hour cap (`discovery-backoff.test.ts`, `discover-new-reviews.job.test.ts`). The sync a sweep starts waits a fixed per-Property offset of up to ten minutes, which spreads one sweep's Google calls without changing how far apart a Property's polls are (`discovery-spread.ts`).
- A Review keeps stable identity — provider content can expire without deleting replies, Inbox work or history, and re-observation reconnects the same Review. A Material Review Revision is created only when the original rating or normalized original guest text changes.
- **Inbox.** An Inbox Item holds numbered Handling Cycles, each anchored to exactly one source revision. Status is only `open | closed`; assignment, escalation, priority and personal seen state are independent (priority is an explicit manager choice; the review-signal level is only a suggestion, ADR 0071); closure records an eligible reason and actor. A material revision, loss of a live provider reply, or another catalogued trigger opens a new cycle, preserves prior history, notifies Responsible Recipients and fences stale drafts. The fence of a guest edit is Review's, in the transaction that records the revision: an open publication is cancelled, a reply awaiting approval and a reply whose publication failed (one whose outcome RepKey never learned included) return to draft with the text their manager wrote, and unedited AI text is withdrawn, so nothing written for the earlier revision reaches Google without a new submission and a new Confirm & Publish; the author and the approvers are told. A manager's own draft and a rejected reply are in nobody's queue and stay as they are (`src/contexts/review/CONTEXT.md`, Model; `guest-edit-reply-fence.integration.test.ts`, `ai-draft-purge.integration.test.ts`).
- Assignment is optional, singular, limited to active AccountAdmins or PropertyManagers with current membership and PropertyAccessGrant, grants no access by itself, and auto-unassigns an invalid assignee. Escalation is an explicit manager action resolved independently of closure.
- The Google Review **Response Target** — not an SLA — defaults to 2,880 minutes (48 h) Organization-wide, AccountAdmin-configurable within 1–43,200 minutes. Timing starts at Google's original publication, historic onboarding imports are excluded (so is a review RepKey could not time: one a relink finds from while the Property was disconnected, or one Google lists after the import's history, though both are announced), a material revision starts a new target, and `Overdue` is derived and never mutates status. A target already overdue when RepKey first observes the review prompts once, with target passed; its halfway reminder is never sent. Before a Google-review reminder is released the job reads that review from Google once: a reply already on Google that RepKey has observed holds the reminder until the normal close cancels it, and a Google that cannot be read delays it by at most 15 minutes from its scheduled time (15 to 20 in practice, as the job runs every five minutes), after which it goes out (`src/contexts/inbox/CONTEXT.md`; `docs/operations/inbox-response-targets.md`). Completion is `confirmed_on_google` **or** `external_current_live` (`src/contexts/inbox/CONTEXT.md`, invariant 12; `src/contexts/inbox/infrastructure/outbox-consumers.test.ts` closes work from each, and `reply-observation-inbox.integration.test.ts` closes it from a live reply written outside RepKey against PostgreSQL); the program document names only the first.
- Reply publication is an explicit **Confirm & Publish** by an authorized manager; the author may confirm their own draft. Bulk Reopen works. Bulk Close does not exist (ADR 0055 decision 13): the bulk status command accepts only `open` (`bulkUpdateStatusDto`; `inbox-server.test.ts`), the command store answers a bulk close with `invalid_input`, "Inbox bulk close is unavailable" (`bulkUpdateStatus` in `inbox-command-store.ts`), and the bulk toolbar offers no close control (`e2e/critical/workflows/inbox-handling-cycle.spec.ts`). There is no `bulk_close` capability or token to switch on.
- Private feedback carries its own Handling Target: Organization default 2,880 minutes with optional Property override, no Portal override. Only an explicit **Mark as handled** with an approved outcome completes it; guest withdrawal cancels it; at most one halfway and one target-passed reminder per active cycle: a halfway already due when the target is recorded is never created, and one still pending once the target has passed is cancelled, so a late release prompts once, with target passed (`response-target.store.integration.test.ts`).
- **AI.** Three separately controlled per-Property capabilities — `review_analysis`, `reply_drafting`, `property_trends`. Analysis and drafting are independent; trends requires analysis. Review analysis (v3, since 2026-10-30) records an overall sentiment, locally derived attention (attention v2) and an optional Urgent reason (safety, health, discrimination or a legal threat), and per review up to a handful of mentions: one of twelve universal topics, a polarity, a strength (mild, clear or strong), a cause of two short lowercase labels of one to three words (a thing and an issue) that never reproduce four words of the review or name a person, the numbers of the sentences the mention comes from, and a result saying whether those sentences name a team member or someone else (never the name). It also keeps per-Property issue groups, daily counts of reviews by star rating, and the Google primary category as input only. It does not copy review text. All capabilities stay off until AccountAdmin AI Authorization, live access, notice version, provider policy and platform gates pass. A consent recorded under a notice no longer in force is refused before any provider work is claimed. Since 2026-10-30 that is every notice but the served one (`merchant-ai-notice-2026-10-30.v1`; §2, RE-CONSENTED 2026-10-30). A refused reply draft answers `consent_renewal_required` and the composer names the notice and who can confirm it, and a review is settled as not analysable until re-consent analyses the history again (`generate-reply-suggestion.test.ts`, `analyze-review-event.test.ts`).
- AccountAdmin owns the maximum authorized capability set and irreversible AI-data erasure. Disabling fences new and in-flight work immediately and hides outputs; erasure purges local derivatives within 24 h while retaining content-free evidence. Re-consent under a changed analysis notice bumps the Review Analysis epoch and the existing enrollment path re-analyses eligible history; other re-enablement reuses data only when lineage, policy, model and freshness remain valid.
- AI processes only eligible Google review content. Private ratings, private feedback, contact details, Inbox notes and manager-internal text never leave for AI. Topic records, causes and issue groups are advisory derivative metadata, and no AI output can mutate Inbox, assignment, escalation, priority, publication, Portal behaviour, Goals or Staff metrics, or send a notification (the Inbox shows the AI's attention level only as a suggestion, ADR 0071). One exception is live since the switch-on of review analysis v3 (2026-10-30): an Urgent finding of review analysis v3 (a reported risk to safety or health, discrimination or a legal threat) raises one content-free alert per review revision, "An urgent review needs you" with a link, to the managers who receive that Property's review notifications, in the app and by email under the reader's existing Action needed preferences. The email carries no reason, rating or review text; the reason shows in the app; and the alert changes no Inbox status, assignment, escalation or priority (ADR 0031 and ADR 0046, amended 2026-10-30).
- **Metrics and goals.** Exactly three Goal measures — `qualified_scans`, `portal_rating_count`, `portal_rating_average` — at Property, Portal Group and individual Portal scope. Portal Results shows five measures — qualified scans, private ratings, the average private rating, guests who opened Google, and private notes — at the same three scopes, so group rows, group pages and totals carry all five (owner decision 2026-09-30; Google opens and private notes are results measures only, never Goal inputs; ADR 0041 amendment). A group's figures are its Portals' readings under the group each Portal had at event time, so a Portal that moves keeps its earlier results with its old group. Person- and Team-scoped goals are prohibited. Reporting defaults to a rolling 30 days against the equally long period before it; Portal Results count whole Property-local days, today included, against the same elapsed time of the preceding days; All Time is absolute with no fabricated trend; missing, stale or insufficient data is never coerced to zero — surfaces show `Data through…`, `Updating`, `Insufficient data` or `Temporarily unavailable`.
- **Property Google rating goal** (owner decision 2026-10-14, ADR 0067). A Property may have one at a time: either a target above the one-decimal rating Google shows plus a chosen weekly pace of new Google reviews, or a watch that Google keeps showing the rating it shows now (no pace). Progress and, for a higher target, a forecast month range are worked out from Google's own rating and review count and the Property's cached Google reviews. It is reached only when Google shows the target, and it has no deadline and no "missed". It is not a Goal Program and not a Goal measure: Goal Programs keep exactly the three measures above, and no Google fact reaches them (`GOAL_METRICS` in `goal-program.ts`, validated by `z.enum(GOAL_METRICS)` in `goal-program.dto.ts`; the `goal_program_versions_metric_check` and `goal_subject_assignments_metric_check` CHECKs in `goal.schema.ts`). AccountAdmins and PropertyManagers with access to the Property see, set, change and end it (`goal.read`, `goal.create`, `goal.update`, `goal.cancel`, under `goal.use`, the one capability switch it shares with Goal Programs); Members never see it. Mandatory account notices name the Organization and role and also cover property-access changes and, for the inviter, an accepted invitation.

## 5. Enforced architecture rules

- **Context boundaries** — layered dependencies and cross-context access only through a public API; every file and import target classified. `eslint.config.js` (`boundaries/*`, `local/cross-context-public-api`) + `scripts/check-architecture-boundary-controls.mjs`, both in `pnpm lint`. Catches domain importing `#/shared/db`, or an unclassified file routing around the policy.
- **Atomic state + fact** — a fact is an `outbox_events` row committed in the same `db.transaction` as the state it describes (`insertOutboxRow`), delivered at-least-once by the worker's relay + dispatcher to catalogued consumers; there is no in-process bus. The commit is held by each context's command store suite against PostgreSQL, where a failed fact insert rolls the state back and a failed receipt rolls the consumer's change back (`src/contexts/*/infrastructure/repositories/*-command-store.test.ts`: `reply-command-store.test.ts` in Review, `inbox-command-store.test.ts` in Inbox, `identity-command-store.test.ts` in Identity and their siblings). The hand-over is held by `src/shared/outbox/relay.test.ts` and `src/shared/outbox/outbox-crash-boundaries.test.ts`: a row stays unpublished until the queue has taken it, is added again under its own id, and a redelivered job that finds its receipt applies nothing; the second file's header lists the seven crash boundaries and where each is held. End to end: `src/shared/outbox/infrastructure/repositories/durable-cutover.test.ts`. Registration: `src/shared/architecture/outbox-consumer-registration.test.ts`. Catches a consumer that acknowledges work it did not do, a fact delivered twice with effect, or a catalogued consumer nobody registers.
- **Tenant scoping** — every repository callable that queries a tenant-owned table restricts a statement to a tenant value the statement filters by; naming `organizationId` in a projection, an assignment, a row mapper, a guard or an unused parameter is not a predicate, in the query builder or in raw SQL. Exemptions are unique, explained, categorised and bound to real code. `tenant-predicate-canary.test.ts`. The registry holds a callable to one restricted statement; an unrestricted statement beside it fails unless it is one of the 43 callables recorded in `tenant-predicate-statement-baseline.ts`, a list that can only shrink.
- **Server-only import protection** — no Node-only module reachable from the browser. `browser-reachability.test.ts` reads the build-time deny list from `vite.config.ts` (`importProtection.client`) and walks what the client build keeps of a server-function module. Catches a component importing a repository or the DB client, and a plain export that keeps a Node builtin in a server-function file.
- **Identifier-only facts** — event payloads carry identifiers and facts, never protected content; a payload field named like free text or like a name (`reason`, `message`, `name`, `slug`, `title`, `note`, …) must be registered with its reason. `content-free-facts.test.ts`. The check goes by field name in the TypeScript payload types: a field named some other way is not asked about, and the stored Zod schemas are not read. The register records that Property and Organization names and slugs ride their durable facts.
- **No auto-publish** — a reply reaches Google only through the `publish-reply` job, only after a human moves it `pending_approval → approved`. `no-auto-publish.test.ts` plus `src/contexts/review/domain/rules.test.ts`; `reply-workflow.property.test.ts` and `reply-publication-workflow.property.test.ts` beside it hold the reply status table and the publication tables to moves written by hand, never to the tables themselves.
- **A reply never replaces an answer RepKey has not seen** (2026-10-21, ADR 0046) — `reviews.reply` is an upsert with no precondition, so the `publish-reply` job reads the review from Google (`reviews.get`, admitted under `property.connect_gbp`) and records it through the writer sync uses before it claims a fresh publication. A reply typed on Google since the last sync moves the observation head the manager authorized against; the cycle then ends as `provider_truth` and nothing is sent, and a reply Google shows without returning its text is treated as a reply that is there. Google no longer having the review ends the cycle as refused; a read that fails is retried and consumes no claim. **Residual:** a reply typed on Google between the read and the write is still replaced (about a second; Google's upsert has no precondition), and a reply Google holds back for moderation is not modelled. Publishing has its own quota lane (`google-reviews-write-v1`), so a sync scan cannot starve it. Evidence: `reply-pre-publish-read.integration.test.ts` (Google answers behind RepKey's back), `publish-reply-preread.test.ts`, the model suite's write-time violation `overwrote a reply on Google that RepKey had not seen`, and `quota-policy-coverage.test.ts`.
- **Guest contact containment** — Contact Request has no activation path and contact fields never leave the Guest context. `guest-contact-containment.test.ts`.
- **Privacy exfiltration** — one synthetic marker crosses logs, traces, Sentry, metrics, outbox and beta feedback and must be scrubbed at every one. `privacy-exfiltration-canary.test.ts`.
- **Provider egress targets** — Google endpoint URLs (any address on `googleapis.com`, fonts aside, or on `accounts.google.com`) exist only in the composition `providerConfigFor` mapping and in the five files the test lists with a reason each: OAuth scope and issuer identifiers, the egress gateway's route catalogue and inventory, the key set for inbound Pub/Sub verification, and the consent-screen address the browser is sent to. No adapter URL, no fallback, one construction site each. `provider-target-selection.test.ts`. Review links on other `google.com` hosts are guest destinations with allow lists of their own, not provider endpoints, and are outside this check.
- **One provider SDK boundary** — the live Google Performance path has no repository, queue, cache or Metric dependency, so a Performance value can never become durable. `google-performance-live-boundary.test.ts`.
- **Tenant-cross schedules decide each tenant** — a tenant-cross schedule firing is admitted before the capability check, so a schedule that holds a capability asks current policy about each Organization and Property before acting for them. `tenant-cross-schedule-authorization.test.ts` covers every scheduled job family whose firing is admitted that way, read as the gate reads it (the schedule row, else the job row; the capability by action). Catches a new schedule that names no decision for its tenants, and one that claims a scope authorizer the worker does not give it. That a handler asks about every candidate is proven per schedule, where a policy suite exists: `review-analysis-backlog-jobs-policy.test.ts` for the Review Analysis drain (and for the ungated analysis consumer, which asks the drain's question before a provider call on delivery and queues a review that arrives during a stop), `invitation-capability-gate.integration.test.ts` for invited registration recovery. One recorded gap: the Response Target reminder release still asks nothing before it acts for an Organization (its in-app reminders flow whatever `inbox.use` says; its emails are decided per Organization). Since 2026-10-21 it also reads one Google review before it releases a Google-review reminder, and that read does ask: it goes through the provider authorizer, which decides per Organization, Property and connection (`property.connect_gbp`, the kill switch, suspension, the grant) and refuses what it should not make, so a refused read releases the reminder exactly as before.
- **Server functions ask the policy** — every `createServerFn` handler reaches `requireExecutionAllowed` in its own module or through a helper of the server adapter layer (`src/contexts/<context>/server/`), or is listed with the guard it asks instead: the public policy for a guest, a per-address admission for sign-in and registration, the operator check for the console, the session for an account with no Organization yet. `server-function-policy.test.ts` reads every declaration; the list is `server-function-policy-exemptions.ts`, each entry bound to the code it names. Catches a handler whose policy call was deleted, a new server function that never asks, a listed exception that no longer matches its handler, and a use of `createServerFn` in a shape the check does not read (anything but a top-level `const`). It proves the call is written on a path from the handler; the action, capability and Property a handler passes are proven by that handler's own tests.

## 7. Operating commitments

Internal engineering objectives, never a customer SLA. ADR 0038 is accepted and makes these targets operational once a production database exists. One does: the closed beta environment (`closed-beta-v2` on Railway, the target of `pnpm ops deploy-ci-images`) is running and serving users, and its PostgreSQL database started empty on 2026-09-05 and has kept its data across every deploy since (`src/shared/db/CONTEXT.md`). It is not disposable, so the targets are in force. **UNVERIFIED — owner to confirm (2026-10-13):** whether they are met. The repository holds no reading of the backup or point-in-time-restore state of that database and no record of a restore drill against it; the one inspection it retains was made in August 2026, before that database existed (`docs/operations/backup-and-lifecycle.md` §1).

- **RPO ≤ 15 minutes**, verified by PITR interval plus restore drill. **RTO ≤ 4 hours**, verified by full restore to operational state.
- Zero data loss from a committed source and zero duplicate externally visible replies, both proven by fault injection.
- Seven stop conditions — any one triggers an immediate stop of all external effects with data preserved: tenant isolation breach; unauthorized Google action; unexplained loss of committed data; duplicate externally visible reply or email; leaked token or secret in logs or responses; inability to restore within RTO; privacy or policy violation.
- **How a stop condition is noticed: mostly by a person.** Automatic detection is **UNENFORCED** except for the partial alerts named here. No alert watches for a tenant isolation breach, an unauthorized Google action, or a leaked token or secret: the tests of §5 and the CI scans hold them before a release, and after it a person finds them in a report, a log line or Sentry. `backup.pitr`, for the ability to restore, is registered and not implemented. The alerts near the other three conditions are partial: `queue.quarantine-nonempty`, `queue.quarantine-growth` and `guest.observation-loss` report work or observations that were dropped, not every loss of committed data; `reply.ambiguous-aging` reports a reply whose outcome on Google is still unknown after its check was due, and nothing detects a duplicate reply or a duplicate email; `retention.failure` reports a retention run that failed, after which content can outlive its deadline, which is one privacy rule and not privacy or policy violations in general. Every implemented alert is evaluated by the worker's own `health-check` job every five minutes (`src/shared/observability/alert-definitions.ts`), so a worker that is down, or one whose Queue Redis or `health-check` scheduler is gone, raises none of them, `worker.heartbeat.stale` included, while web stays ready because the worker heartbeat is not a readiness input (`src/shared/health/readiness.ts`). `web.availability`, the external probe the code gives this case to, is registered and not implemented, and a probe of web alone would not notice, because web stays ready: it has to read the worker heartbeat on `/api/health/metrics` as well. Nothing in this repository sets up a check from outside the deployment, so whether one exists and reads that heartbeat is the owner's to state. `src/shared/observability/alert-documents.test.ts` holds every alert named here to the registry.
- Stop procedure: set `BETA_CAPABILITIES_OFF` (`1|true|all` kills everything, a comma list kills exactly those), stop schedulers, preserve canonical data, drain or quarantine queues, follow the incident runbook.
- **Recovery is forward-only** (owner decision 2026-10-12, ADR 0038 amendment). A bad release is contained with the stop procedure above and repaired by deploying a fix forward; an earlier image is never a containment or recovery step. An image older than the migrations already applied is refused on purpose: web's predeploy runner (`scripts/migrate-deploy.ts`) and `/api/health/ready` both require the applied migration count to equal the image's journal, and the runner says `This image is older than the database` rather than promising that a rerun converges (`src/shared/db/migration-journal-state.test.ts`, `src/shared/health/readiness-migration-journal.test.ts`, and the real runner against a database one migration ahead in `src/composition/declared-capability-posture.deploy.integration.test.ts`). The gate is web's: nothing checks a worker or provider Redis image against the applied migrations, so `pnpm ops deploy-ci-images` (web first, stops when web is refused) is the only supported deploy path, and Railway's own Rollback or Redeploy of an earlier deployment is never used on any service. A fix keeps every migration file and journal entry the database has applied: a plain revert of a commit that touched `drizzle/` deletes one, passes CI, and is refused by the same gate. Point-in-time restore stays reserved for data loss. Operator steps: `docs/operations/runbooks.md` §28.
- Every deviation needs a signed exception naming reachability, mitigation, owner, expiry and remediation issue. Exceptions auto-expire.

### Draft usage measurement (Phase 1 B3a, 2026-10-31)

Reply drafting v1 and v2 record first-party usage metadata immediately on deploy,
independently of the dark v2 rollout. One `ai_draft_measurements` row represents a
logical provider generation, keyed by tenant, actor and drafting request key. An
automatic rewrite is its second independently admitted provider attempt. Local
catalogue fallbacks and refusals before any provider operation are not provider
generations. Rows hold controlled generation attributes, timestamps, button flags
and bounded edit scalars (rating bands: 1–2 low, 3 middle, 4–5 high), never draft/review text, avoidance terms, rejected output
or text fingerprints. No new provider payload or notice version is introduced.

`ai_draft_measurement_links` associates Reply revisions with those generations.
It is measurement only: a manager save still ends AI authorship and clears active
AI provenance. Adoption, submission and Google-observed publication commit their
measurement in the corresponding transaction. Approval, dispatch and provider
acknowledgement do not count as publication. Advisory client events cannot grant
access, alter a reply or relax a publication or withdrawal fence.

The browser calculates character Levenshtein distance over Unicode scalar values
after NFC, whitespace collapse and trimming, divided by the longer normalized
length (two empty strings have distance zero). Its adopted baseline lives only in
compose-session memory, including Undo history. A reload preserves the measurement
identity but loses that baseline; submission records unavailable rather than zero.
Scalars are accepted only for the generation and saved Reply revision submitted.

Organization export includes generation rows and revision links under enabled merchant
authorization, with independent measurement IDs and no operation IDs or request keys. Organization
purge, Property deletion and disabling or revoking Reply Drafting consent for a
Property erase them. Profile, Google binding, material Review revisions and execution
control changes retain them; deletion of the owning
`ai_operations` metadata cascades to the generation and its links, so measurement
shares that metadata retention, with no independent extension or text cache.
There is no new age-based deletion rule for operation metadata in this PR.

`pnpm ops ai drafts-report --operator <id> [--since <ISO timestamp>]
[--property <UUID>]` uses the existing named-operator read harness and prints
aggregates only: generation groups, adoption, refusals, rewrite rate, button/event
counts, confirmed publication, distance and latency percentiles. Adoption rate is
adopted / ready generations. Sent-unchanged share uses submitted drafts with an
available distance; unavailable submissions are counted separately.
