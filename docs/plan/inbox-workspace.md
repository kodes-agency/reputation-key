# Inbox workspace — the queue rail and the list (panels 1 and 2)

Status: **planned, not started.** Follows `inbox-detail-v2.md` (v2.1, shipped on
`ux/inbox-detail` as `8593cd0b` … `a9843409`); every file:line below is against
`a9843409`. Canvas, rev 3 (direction A chosen; B kept on page 2 for reference):
https://claude.ai/code/artifact/dec2bbe1-c0f3-4f03-8177-79d3cff9c300

The detail pane is out of scope here except where a shared file must change
(`inbox-page-v2.tsx`, the row's reply chip, the reopen dialog it already shares
with the bulk bar).

## Why

Reviewed on real data after v2.1, the first two panels are where the inbox still
reads as an email client rather than a place to answer reviews. Each finding
traces to code:

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **The inbox hides the app.** `_authenticated.tsx:195` computes `isInbox` and `:199` renders `null` in place of any sidebar. The only ways back are the folder panel's `Back to app` / `Dashboard` links (`inbox-sidebar.tsx:66-78`). The provider still mounts, so ⌘B (`ui/sidebar.tsx:95-105`) and the top bar's `SidebarTrigger` (`app-top-bar.tsx:51`) toggle a sidebar that is not there — and every `tooltip` on the inbox's own `SidebarMenuButton`s is governed by that invisible state (`ui/sidebar.tsx:530`). |
| 2   | **Scope has two homes that disagree.** In the inbox, scope is `PropertyFilterSelect` (`property-filter-select.tsx`), which renders nothing for a one-property workspace (`:20`) and is the only control with an _All properties_ choice. | 3   | **Three folders cannot say what the work is.** `folders` (`inbox-sidebar-items.tsx:8-12`) are Open · Escalated · Closed. _Open_ mixes reviews that need a first reply, replies waiting for a manager's approval, replies in flight to Google and private feedback that needs handling. The only signal is one chip at the tail of the snippet (`inbox-list-v2.tsx:123`); an escalated item is not marked on its row at all.                                                                                            |
| 4   | **Dead categories.** Facebook and Yelp (`inbox-sidebar-items.tsx:16-17`) filter `platform=`, which only ever holds `google`. | 5   | **Chrome outweighs content.** The list header is an `h1` row plus a search row (`inbox-list-header.tsx:44-96`, 116 px measured); three rows need 288 px. Applied filters are invisible once the popover closes except as a count badge (`inbox-filter-popover.tsx:61`), and the title (`Open reviews`, `inbox-page-parts.tsx:66-70`) never says which property you are looking at.                                                                                                                                     |
| 6   | **Rows change height with their content.** The snippet is `line-clamp-2` only when there is text (`inbox-list-v2.tsx:112-121`) and the chips sit in the same flex row as the snippet, so a row is one, two or three lines depending on what it carries — and the first canvas made it worse by giving the assignee a line of its own.                                                                                                                                                                                  |

| 8   | **The active row is a side stripe** — `border-l-2 border-l-primary` (`inbox-list-v2.tsx:63-64`), which `DESIGN.md:267` names as never intentional.                                                                                                                                                                                                                                                                                                                                                                     |
| 9   | **Every row wears a checkbox** (`inbox-list-v2.tsx:67-77`) for two bulk actions most sessions never use. `Load more` (`inbox-list-panel-parts.tsx:92`) says nothing about how many remain. The shortcuts (`use-inbox-keyboard-shortcuts.ts:168-192`) have no legend anywhere. Nothing marks what is new: the visit watermark (`inbox_user_views.last_inbox_view`) feeds only the nav badge (`manager-nav-items.tsx:145-149`), which the inbox route hides.                                                             |
| 10  | **The phone has a second drawer.** Below `md` the inbox opens its own `Folders & categories` sheet (`inbox-page-v2.tsx:142-165`) while the app's own sheet is unreachable, because no sidebar is mounted for the trigger to open.                                                                                                                                                                                                                                                                                      |

## What the code says

Facts the design has to respect. None is a guess; each was read at `a9843409`.

- **Reply state lives in another context and is loaded per page.** `get-inbox-items.ts:105-125`
  batch-loads it through `ReplyLookupPort.getReplyStatesByReviewIds` (adapter
  `reply-lookup.adapter.ts:26-35`, `internal` wins over `google_sync`; SQL in
  the Review context, `reply.repository.ts:130-158`), for review rows only and
  only for a caller with `reply.manage`. `inbox_items` has no reply-state column
  (`inbox.schema.ts:38-118`); nothing counts or filters by it today.
- **Status is the handling-cycle head, not the column** (`inbox.repository.ts:93-98`);
  every read left-joins `inbox_handling_cycle_heads` (`:83-91`). Counts go through
  `countWhere` (`:143-166`) with the same join.
- **`assigned_to` has no index and no filter** — not in `InboxFilters`
  (`ports/inbox.repository.ts:26-45`), not in `getInboxItemsDto`.
- **Exactly two bulk commands.** `bulkAssignInboxItemsFn` (`inbox-item-actions.ts:59-90`;
  use case needs `inbox.write` AND `inbox.manage`, all-or-nothing) and
  `bulkUpdateInboxStatusFn` (`inbox-status.ts:61-92`; `status: z.literal('open')`,
  reason required, `dto/inbox.dto.ts:99-136`). Bulk close is disabled by design
  (ADR 0055 §13). `INBOX_BULK_LIMIT = 100` (`dto/inbox.dto.ts:11`).

  (`inbox.schema.ts:947-957`), upserted monotonically (`inbox-view.repository.ts:15-53`),
