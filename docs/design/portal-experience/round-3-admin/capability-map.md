# Portal admin capability map

Source: `the repository` at current main `878268bf1`, read-only. All paths below are relative to `src/` unless they start with `docs/`.

This map exists so every admin proposal can separate **what exists** (server function, use case, data) from **what is new**. "Exists" refers to the server and domain. The Notes column says whether a UI uses it today.

**Legend**

- Exists?: `yes` = a server entry point plus a use case exist. `partial` = only some of it exists, or it exists without an entry point, or the UI misrepresents it. `no` = nothing exists.
- Roles: `AA` = AccountAdmin (better-auth `owner`), `PM` = PropertyManager (`admin`), `M` = Member (`member`).
- Every admin page sits under the property shell `routes/_authenticated/properties/$propertyId.tsx:18-22`, which requires `property.admin`. Only AA and PM have that permission, so **Members never reach any portal admin page**, even though they hold `portal.read`. Member login is also inactive in the beta.

### Dimensions, scopes and ranges available

- **Scopes:** organization (fleet, org-wide `listPortals`), property, portal group (Goals only, plus `portalGroupId` on qualified scans at event time), portal.
- **Dimensions:** star value 1-5; `property_local_date` (daily); destination kind (Google or secondary link); access-artifact channel (QR or NFC), which lives only in `guest_qualified_scans` and is not in `metric_readings`; publication version; health reason.
- **Ranges:** portal analytics presets `7d`, `30d`, `60d`, `90d`, `180d` and `all`, with an equal prior window for bounded ranges. The dashboard uses `30d`, `90d`, `180d` and `all` (default 90d, URL `?range=`). Goals use calendar months. Lifetime covers everything.
- **Freshness contract:** every governed family returns evidence (state, reason, completeness, `verifiedThrough`, `correctionHead`). The lifetime view returns its reconciliation and seal times. Fleet returns a watermark and freshness. Goals return `sourceCompleteThrough` and a reconciliation status. This is enough to render "availability by exception" with provenance on demand.
- **Hard rules on the data:** never show staff attribution (`guest_qualified_scans.attributed_staff_*`), leaderboards, badges or quotas. Never call Google selections "reviews". Keep the 10-rating comparison floor.

## Gaps the redesign will need

**A. UI only. The server already supports it.**

1. A rollback action in a publication ledger (`rollbackPortalPublication`).
2. A publish checklist assembled from existing reads: token, manager, Google destination, brand profile, and content per locale. Label each item with who can fix it (AA or PM).
3. Link approval status shown in place, by joining links to approved destinations client-side.
4. Portal scans and feedback on the property overview (`getPropertyOverviewFn` `kpis.scans` and `kpis.feedback`) and on the All properties list (fleet `scanCount`, `feedbackCount`).
5. An org-wide portals list from `listPortals` without `propertyId`.
6. Pending-change facts ("3 unpublished changes: brand colours, Spa override…") from `getPortalPublicationHistory.pendingChanges`.
7. One primary action per area, replacing six or more save buttons. This is possible with the existing commands, called in sequence or batched.
8. Align the portal analytics range model and default with the dashboard (`?range=`, rolling windows).
9. Rename "Review Clicks" and "Scans". Relabel the threshold setting.
10. Retire the legacy theme presets and list swatch, and show the real brand profile instead.

**B. New reads (no new domain rules).**

1. Portal health, current and history, batched per property for list columns, filters, the property overview and the detail ledger. Uses the existing `getCurrent` and `listHistory`.
2. A portal list projection: health, live version, pending-change count, group, manager count, token status and recent qualified scans in one batched read, to avoid N+1 calls.
3. The publication history actor (`activatedBy`), plus a read of the last content review.
4. Snapshot content (a given version) and the working copy rendered as a guest DTO, for a faithful preview and rollback confirmation. A field-level draft-versus-live diff.
5. A property-level list of affected portals for a property-wide edit (from `portal_pending_content_changes`).
6. "Guests who opened Google" and secondary-link selections as separate measures (filter by `portal_destination_kind`).
7. Property- and group-scope portal analytics. Scans and feedback already allow property and group scope in the registry. Private ratings are `['portal']` only in analytics. Either widen the registry (a governance decision) or expose `queryGoalMetric` (monthly `qualified_scans`, `portal_rating_count`, `portal_rating_average` at property, group and portal scope) through a server function.
8. A QR versus NFC split through `guest_qualified_scans.access_artifact_id` joined to the artifact channel, subject to the undecided retention.
9. A `portalId` filter or facet in the Inbox Feedback queue, and a deep link from portal analytics to "this portal's private notes".
10. A list of guest responses under review, so the existing `moderateGuestResponseFn` has a surface.
11. Token and access-artifact history, if the ledger should show address events.

**C. New commands or model changes (need product decisions).**

1. **Publish changes while live**: a new snapshot without disabling. Today `published` to `published` is a no-op.
2. A composition choice (A, B, C) on the property brand profile, plus the derived-token engine and a primary-contrast gate at publish (today only text contrast is enforced).
3. Localized (EN/BG) link labels and category titles. Render `iconKey` from a curated icon set.
4. Placement naming and several access artifacts per portal (named QR or NFC per table or room). Print templates. Re-downloading the address without rotating is a security decision.
5. Duplicate a portal, or start from a template.
6. "Republish to adopt new guest copy" when a new language-pack version ships.
7. Health reconciliation on token revocation and grace expiry (verify first). Possibly a health reason for approved destinations that lapsed silently.
8. A `needs_admin` state for the setup step `portal_published` when AA-only prerequisites are missing.
9. "Try as guest" simulation that writes no responses or analytics and never navigates to Google.

**D. Inconsistencies every proposal must account for.**

1. **Permission mismatches:** a PM sees Delete on links and categories but the server requires `portal.delete` (AA). Archive is AA-only in the UI but PM-allowed at the server.
2. **Same label, different measure:** "Scans" is `portal.scan` for bounded ranges but qualified scans for All time and in Goals.
3. **"Review Clicks"** adds Google and secondary-link selections together, in both bounded and lifetime views.
4. **The preview is not the guest page:** it uses legacy portal name, description and theme, and the organisation name.
5. Portal name, description and theme do not reach guests on v2 snapshots. The guest h1 is the localized override or the property title.
6. Members hold `portal.read` but cannot open any portal page (the property shell requires `property.admin`). Treat Member as having no portal admin surface in the beta.
7. Brand profile, property fallback content and destination approval are AA-only. The PM-facing flow must show "waiting for an Account Admin", not a dead button.
8. Image upload is safety-blocked (`portal.upload`). Any photo or logo slot must render a no-photo state.
9. The data model contains staff-attribution columns and `badge`/`leaderboard` consumer entries. The admin must never read or display them.
