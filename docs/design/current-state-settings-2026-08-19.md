## 2. Scope collisions and mislabelled copy

### Collision 1 — Notifications mixes three scopes behind a property-scoped page description

`notifications.tsx:67` sets the page description to _"Control property-specific in-app and email delivery."_ The same page writes `notification_user_settings`, whose uniqueness key is `(userId, organizationId)` only — `notification.schema.ts:187-189`. Locale and timezone are therefore org-wide for the user and cannot be varied per property, contradicting the header.

The governance catalogue independently records this route's scope as `organization`, not `property`: `src/shared/governance/entry-point-catalogue.ts:2015-2021`.

The copy compounds the confusion inside the page: the "Language and timezone" card description reads _"Used for notification formatting. Daily digests remain property-local."_ (`notifications-settings-view.tsx:78-80`) — an org-scoped control annotated with a property-scoped caveat.

### Collision 2 — Notification preferences advertised in two places, one of them stale

`/settings/preferences` renders a dedicated Notifications card reading _"Manage email and in-app notification preferences. Coming soon."_ — `preferences-settings-page.tsx:29-38`, dimmed with `className="opacity-60"` at `:28`. `/settings/notifications` already ships exactly that. Both entries are unconditionally present in the sidebar (`settings-sidebar.tsx:43-47` and `:71-76`), so a user sees a live Notifications nav item and a "coming soon" Notifications card one click apart.

### Hide vs disable

- **Navigation: hidden.** `settings-sidebar.tsx:52-106` conditionally builds the Organization, Members, Recognition, AI and Integrations entries from `can(...)`. Profile, Security, Preferences and Notifications are unconditional (`:42-48`, `:71-76`).
- **Direct navigation: redirected, never disabled.** Every gated route throws `redirect({ to: '/settings/profile' })`. There is no "you do not have access" state anywhere under `/settings`.
- **Capability denial diverges from permission denial.** Recognition sends capability denials to `/unavailable` (`controlled-route-gate.ts:16-21`) rather than to `/settings/profile`. It also only runs that check when `?propertyId` is present (`recognition.tsx:26`), so a paramless visit bypasses the capability gate entirely and renders the "select a property" card.
- **In-page gating is inconsistent.** `members.tsx:129` hides the Invite action behind `canDo('invitation.create')`. `portal-settings.tsx:71`, `:110`, `:117` mix hiding and disabling on `can('portal.update')`. The notifications view calls `usePermissions()` **not at all** and renders every control unconditionally — which is what makes defect S6 user-visible.
- **Role-escalation ceiling.** The members loader caps assignable roles: `AccountAdmin` is offered only to an actor who already holds it (`members.tsx:79-81`), and the components re-check internally (documented as defence in depth, `members.tsx:4-5`).

### Named divergences

1. **Validation source.** Stack A imports schemas from `contexts/*/application/dto/*` (`security-settings-form.tsx:17`, `organization-settings-form.tsx:21`) — except `profile-settings-form.tsx:24-28`, which declares `profileSchema` inline in the component. 2. **Error surface.** Four different mechanisms: `FormErrorBanner` (Stack A), `FieldError` (merchant-AI only), inline `<p>` (response-SLA only), `toast.error` (notifications, integrations). Recognition has none.
3. **Submit control.** `SubmitButton` (Stack A) vs shadcn `Button` (`response-sla-card.tsx:56`, `integrations-settings-page.tsx:89`) vs raw `<button className=...>` (`notifications-settings-view.tsx:97`, `quiet-hours-editor.tsx:36`, `recognition-activation-card.tsx:165`, `recognition-settings-page.tsx:169`).
4. **Field primitives.** `FormTextField`/`Field`/`FieldLabel` (Stack A, merchant-AI) vs `Label`+`Input` (response-SLA, notifications) vs bare `<input className=...>` (`recognition-activation-card.tsx:53`, `:100`, `:126`, `:137`, `:148`, `:158`; `recognition-settings-page.tsx:161`).
5. **Select primitive.** shadcn `Select` in exactly one place (`merchant-ai-settings-content.tsx:59-75`); native `<select>` everywhere else — notifications x2 (`:61`, `:153`), recognition x3 (`recognition-activation-card.tsx:65`, `:83`, `:113`).
6. **Save model.** Explicit submit on every settings screen except notifications, which persists on every switch/select change (`notifications-settings-view.tsx:134`, `:145`, `:158`, `:186`) while still rendering two explicit "Save …" buttons for the rest of its controls.
7. **Cancel affordance.** Only the three Stack-A forms render one, and all three point at `/settings/profile` (`profile-settings-form.tsx:131-133`, `security-settings-form.tsx:103-105`, `organization-settings-form.tsx:123-125`) — meaning Cancel on the Profile page links to the page you are already on.
8. **Toast ownership.** `useActionMutation`'s `successMessage` at the route (`organization.tsx:74`, `integrations.tsx:47`, `recognition.tsx:53`, `ai.tsx:48-58`) vs component-level `toast.success` (`notifications-settings-page.tsx:95`, `:114`; `profile-settings-form.tsx:79`). Notifications is the only screen using both patterns for sibling actions within one component.
