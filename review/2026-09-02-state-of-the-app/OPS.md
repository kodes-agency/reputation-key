# Operations, deployment, and release — state of the app, 2026-09-02

## Verdict

The production-shaped code and the production deployment have diverged: the live application is still the legacy `reputation-key/google-closed-beta` graph, not the mandated dedicated US `reputation-key-us-beta/cell-us`, and its running services do not share one candidate manifest. All twelve Railway services reported platform status `SUCCESS`, yet an authenticated operational read at 2026-09-02T20:54Z reported `jobs.ready=false`, one repair-required job, and 19 dead letters; neither Sentry nor an operator alert webhook was configured. The target project, rehearsal project, custom domain, schema-migrator deployment, object-store binding, backup proof, restore drill, candidate manifest, deployed journeys, and canary evidence do not exist. The repository now contains a serious, fail-closed immutable build/promotion design, and the latest main CI completed all seven release-prerequisite jobs successfully, but the release-image workflow has never run and those mechanisms have not produced or promoted a release. Four Google/AI sidecars are justified by real credential, provider-network, signing, or control-database boundaries; two provider sandboxes in the live production environment are not. The recovery design remains blocked by a same-database erasure ledger that a PITR restore necessarily rolls back. Gate E and REL-01/Gate F are therefore not achieved, and the pre-rewrite risk of false confidence persists at the exact repository-to-runtime seam the rewrite was intended to close.

## What was achieved

### OPS-A1 The immutable release implementation is real, coherent, and fail-closed

**Evidence.** The fixed contract requires one build and exact-byte promotion (`docs/comprehensive-beta-implementation-program-2026-08-25.md:116-124`). Release Images binds a successful same-SHA main run and seven named jobs before building (`.github/workflows/release-images.yml:36-98`), builds eight image/artifact roles (`.github/workflows/release-images.yml:100-132`), and publishes, SBOMs, scans, signs, and records provenance for digest-pinned images (`.github/workflows/release-images.yml:161-228`). The promotion source parser accepts only registry `@sha256` references and a canonical staged prefix (`.railway/service-source-map.ts:45-76,143-166`). `release:beta` verifies signature/provenance, waits for terminal deployment success, and checks every service's SHA, manifest, digest, auth origin and readiness (`scripts/release/deploy-beta.ts:17-56`). `gh run view 33675157116 --repo kodes-agency/reputation-key --json jobs` returned `success` for `check`, `docker`, `secrets`, `storybook`, `storybook-test`, `e2e`, and `beta-acceptance`; the run completed at 2026-09-02T20:17:23Z for SHA `1425966fcf2f0404f0133478edb81cc41e48f586`. This is ACHIEVED as repository implementation, not as a deployed release.

**Why it matters.** This directly fixes the unsafe working-tree deployment shape identified as pre-rewrite OPS-05 and makes stale or mixed bytes mechanically rejectable.

**Recommendation.** Preserve the one-build/one-manifest design and its no-retry/write-once rules. Do not weaken it to make the legacy deployment pass; operate it against the target graph.

**Cost/risk of the fix.** No design fix is required. The remaining cost is operating-owner/counsel/platform execution; bypassing any prerequisite would recreate the original provenance defect.

**Evidence.** `local:doctor` is explicitly read-only and checks exact Node/ICU, Docker, five ports, stale stacks, Docker memory and disk (`scripts/local-doctor.mjs:1-32,37-87,114-171`). **Cost/risk of the fix.** Already delivered. Its workstation-specific result is diagnostic evidence, not a clean-clone benchmark.

## What is genuinely good

### OPS-G1 The private operations snapshot exposed a real failure that Railway status hid

**Evidence.** `/api/health/metrics` is token-gated, returns 404 on missing/wrong credentials, is no-store, and reads the one composition-owned snapshot (`src/routes/api/health/metrics.ts:1-38`). The reader budgets six sections, reports deterministic `degraded` markers, includes queue depth, worker heartbeat, runtime, migration, release and job state, and remains identifier-only (`src/shared/health/operations-snapshot.ts:1-17,332-442`). At 2026-09-02T20:54:52Z, an authorized GET returned HTTP 200 with `degraded:[]`, migration version 178, a fresh worker heartbeat, but `jobs.ready:false`, 38 jobs, one failing/repair-required job and 19 dead letters; `sync-property-reviews` was the failing job. At the same time, Railway environment status returned `SUCCESS` for all twelve services and public `/api/health/ready` returned all four web dependency checks true.

**Why it matters.** This is load-bearing observability, not a catalogue: it found an active product-runtime failure that the platform could not see.

**Recommendation.** Keep this read model and make it the data source for paging and a small operator cockpit; never expose its token or widen its payload to tenant content.

**Cost/risk of the fix.** Low to preserve; medium to add a supported consumer. The primary risk is treating HTTP 200 as healthy without inspecting `jobs.ready` and `degraded`.

## What should be improved

### OPS-I1 Give the one real operator a supported read-only cockpit

**Evidence.** The authoritative 2026-09-02 capability snapshot required `railway ssh` into `web` and an inline 30-line map of direct SQL queries (`docs/operations/capability-state-2026-09-02.md:162-212`). The codebase itself records `policy-admin.ts` as “awaiting UI wiring” (`src/contexts/CONTEXT.md:85-92`); its useful read-only decision explainer is implemented (`src/contexts/identity/server/policy-admin.ts:317-361`) but not reached by a route. Repository search found `operationsSnapshot` consumed by only `/api/health/metrics` in routes. Five of eight support journey signals are `external_configuration_required` (`src/shared/observability/beta-support-operations.ts:39-126`).

**Why it matters.** For one tenant and six properties, SSH plus ad-hoc SQL is slower and riskier than the product state being diagnosed. It also leaves capability refusal, freshness, job repair, release identity, and backups in separate tools.

**Recommendation.** Wire one authenticated, read-only operations screen or CLI to existing canonical readers: release SHA/manifest per service; backup/PITR receipt age; `jobs.ready`/DLQ/repair state; the six properties' provider freshness; capability/refusal explanation; worker/queue/outbox state; synthetic-journey status. Do not build a second model or a generic admin framework.

**Cost/risk of the fix.** Medium: one narrow server interface plus one table-driven surface. Primary risk is exposing cross-tenant data; keep it identifier-only, AccountAdmin/operator-authorized, audited, and single-tenant scoped.

### OPS-I2 Split the daily development loop from the full release rehearsal

**Evidence.** README's quick path is five manual steps and assumes external Postgres plus several secrets (`README.md:5-33`). The full controller builds nine images, each with its own install, under a parallelism cap needed to avoid Docker OOM (`scripts/local-stack/stack.ts:1690-1725`); it documents about 200 seconds for a full down/up (`scripts/local-stack/stack.ts:2661-2667`). The doctor says 6 GiB minimum and 8 GiB comfortable and warns that repeated images are never collected (`scripts/local-doctor.mjs:114-158`). Four package aliases are exact duplicates of `e2e:stack:*` (`package.json:40-51`).

**Why it matters.** The full stack is appropriate release evidence, but it is disproportionate as the default feedback loop for a one-tenant beta and encourages developers to avoid production-shaped checks altogether.

**Recommendation.** Keep the full acceptance profile; add a documented reduced daily profile (web, worker only when needed, Postgres, cache/queue Redis, one selected provider fixture), share dependency/build cache stages across images, and add repo-scoped stale-image cleanup. Delete the four duplicate `local:stack:*` aliases or make them the distinct reduced profile.

**Cost/risk of the fix.** Medium build-system work, low product risk. The reduced profile must never be relabelled as release evidence.

### OPS-I3 Finish branch protection and make “Simulation” an actual required simulation

**Evidence.** GitHub readback returned `strict:false`, no required pull-request reviews, `enforce_admins:false`, five required contexts, and no rulesets. CI's own comment still says “main carries no branch protection” (`.github/workflows/ci.yml:961-970`), so governance prose already drifted from platform state. Release preflight expects seven successful jobs (`.github/workflows/release-images.yml:43-64`), but branch protection does not require `storybook`, `storybook-test`, or `beta-acceptance` by name. The Simulation workflow path filter omits `drizzle/**`, package/lock/runtime inputs and Dockerfiles, and its only execution is `pnpm seed -- --invariants`, not `pnpm simulate` (`.github/workflows/simulation.yml:3-12,64-87`).

**Why it matters.** A merged SHA can meet branch protection without the full candidate prerequisites, and changes that alter simulation inputs can skip the separately named workflow. This is a real gap between REG-03's required-check claim and the merge authority.

**Recommendation.** Make one fail-closed aggregate status depend on the exact PR gate set; require it with strict up-to-date branches and recorded review (including the solo-beta exception). Either run `pnpm simulate` in this workflow and cover all of its inputs, or delete the misleading workflow and make simulation a named shard of the required aggregate.

**Cost/risk of the fix.** Low-to-medium CI/config work. Runtime cost can remain bounded by path-aware internal test selection, but the required aggregate itself must not disappear.

### OPS-I4 Collapse configuration aliases after cutover, not before it

**Evidence.** `.railway/legacy-config-ownership.ts` declares six root configs as already migrated and says they must be deleted at cutover, while four test/rehearsal configs remain out of graph (`.railway/legacy-config-ownership.ts:31-87`). **Why it matters.** The LOC is not inherently bad; dual ownership and many nearly identical entry points are. At this beta scale, operators cannot reliably remember which of 176 aliases is authoritative.

Replace the specialized tsup files with one table/config factory while retaining distinct bundles. Merge the operator narrative in `immutable-release-promotion.md` and `railway-data-cells.md` behind one executable runbook entry point; keep evidence schemas separate.

**Recommendation.** Delete the posture exception as part of—not before—the cutover. **Cost/risk of the fix.** High platform/operational cost and a migration/cutover risk. The repository already contains the safer source-less foundation, saved-plan, exact-domain and staged-promotion controllers; using the legacy graph to avoid that cost is the defect.

### OPS-S2 Backups and recovery are neither present nor logically complete

**Evidence.** REG-04 requires scheduled backups/PITR, an off-project export and an isolated sibling restore with fresh Redis and cutover/rollback (`docs/comprehensive-beta-implementation-program-2026-08-25.md:575-596`). The target project is absent, so target backups cannot exist. The latest retained direct platform observation says legacy backups/PITR were disabled on 2026-08-29 (`docs/program-completion-plan-2026-08-29.md:27-31`); current legacy backup status is unverified. Repository globbing found no live recovery artifact; the closest local pack explicitly marks every fault scenario and RPO/RTO unexecuted (`docs/release-evidence/beta/bqc8-local-verified/scale-and-recovery.md:43-60,93-98`). `release:rehearse-recovery` only assembles operator/platform receipts and explicitly performs no recovery (`scripts/release/rehearse-recovery.ts:16-24`). More seriously, `applyRestoreResurrectionFence` reads the erasure ledger from the restored database transaction itself (`src/shared/db/lifecycle/backup-erasure-ledger.ts:245-257,368-423`), so a PITR before an erasure also erases the evidence needed to re-erase resurrected data; the independent review confirmed this as high (`docs/release-evidence/review/independent-review-2026-08-29.json:287-289,332-334`). The real `ops:restore-verify` composes retention and the general recovery fence but never calls the resurrection fence (`scripts/ops/restore-verify.ts:27-49,66-119`).

**Why it matters.** There is no recoverable release and no evidence that the one tenant's state can survive database loss without replaying old external effects or resurrecting erased data. Destructive lifecycle contributors are currently deliberately uncomposed, which limits present resurrection reachability, but it does not satisfy the mandatory pre-customer recovery contract.

**Recommendation.** Enable target Postgres backups/PITR and scheduled bucket/volume backup, plus an encrypted region-compliant logical export outside the source project/account. Mirror the append-only erasure ledger off-cell/off-cluster or export it immediately before restore, bind it to restore evidence, compose every required replayer into `ops:restore-verify`, and fail cutover if any entry is absent/unreplayed. Then execute one actual sibling Postgres + three fresh Redis restore, measure RPO/RTO, verify tenant/content counts and effect fences, cut over, roll back, and retain platform receipts.

**Cost/risk of the fix.** High: storage/platform spend, external evidence ownership and a destructive drill. The risk of skipping it is unrecoverable loss or privacy resurrection; a local fixture cannot substitute.

### OPS-S3 Production can be platform-green while the application is unready and nobody is paged

**Evidence.** The deployed-production guard requires `RAILWAY_ENVIRONMENT_NAME` to start with `cell-`; the legacy production environment therefore permits absent Sentry and logs “Error monitoring disabled outside a deployed production Data Cell” (`src/shared/observability/telemetry.ts:477-514,591-601`). Railway variables on 2026-09-02 had no `SENTRY_DSN` and no `ALERT_WEBHOOK_URL`; live web logs emitted that disabled message at 18:52:19Z. Alert dispatch always logs but sends externally only when the optional webhook exists (`src/shared/observability/alert-dispatcher.ts:1-16,39-46,69-96`), and the health job otherwise marks firing after dispatch (`src/shared/jobs/health-check.job.ts:79-128`). Web readiness deliberately excludes worker state and delegates that to metrics alerting (`src/routes/api/health/ready.ts:1-10`), while live Railway probes only liveness. The operations snapshot's degraded health fallback intentionally zeros all problem counters (`src/shared/health/operations-snapshot.ts:194-270`), but `grep "degraded" src/shared/observability/alert-definitions.ts` returned no matches. The live snapshot then demonstrated the consequence: 19 DLQ rows and `jobs.ready=false` while Railway and public readiness stayed green.

**Why it matters.** The current state blocks review freshness for a real property and violates the mandatory automated-monitoring/incident-alert contract (`docs/comprehensive-beta-implementation-program-2026-08-25.md:107-114`). Logs are not a pager, and an unconsumed degraded marker can make unknown health look numerically healthy.

**Recommendation.** Key mandatory observability on production release posture/identity, not a future environment-name prefix.
