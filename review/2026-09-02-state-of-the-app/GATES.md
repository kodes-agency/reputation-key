# Gates, governance, and proportionality — state of the app, 2026-09-02

## Verdict

The rewrite built several real, high-value controls, but gate governance still recreates the pre-rewrite false-confidence failure: the repository inventories 116 gates while the supposed central policy declares only eight and no workflow or hook calls `pnpm gate`. The new `static`/`test-unit`/`test-integration`/`artifacts` split is the clearest success: on the measured PR run it reduced the `check` wall from 1,110s to about 372s (66.5%) while runner compute rose only from 1,110s to 1,117s (0.6%). That run was nevertheless red: the old topology assertion failed after all 12,706 unit tests passed, and critical E2E reproducibly missed one Portal scan; current HEAD fixes the topology assertion locally but has no full CI result. Main is protected and five contexts are required, yet branch protection, release preflight, Gate F, CodeQL, simulation, and Fallow disagree about what “releasable” means. Gate F is not reachable from a workflow, its fixed 18-item list ignores posture policy, and its blanket distinct-attester plus distinct support/incident-owner rules cannot be satisfied by the one-participant beta. The 43 standards exceptions are all owned and unexpired today, but the checker never compares expiry/review dates with today; 32 exceptions exist only because two universal maintainability rules are excepted for 15/17 and 17/17 contexts. Against SAFE-05/GOV-01/GOV-02/REL-01, the executable safety floor is materially better, but external-beta release governance still needs substantial simplification and one generated source of truth.

## What was achieved

### G-A01 SAFE-05 closed the concrete validation blind spots

**Evidence.** `node scripts/check-architecture-boundary-controls.mjs` returned `OK — 24 invalid imports rejected; 14 valid seams accepted` in 4.63s on current HEAD. The checker contains explicit invalid and valid in-memory fixture matrices (`scripts/check-architecture-boundary-controls.mjs:1-25,27-170,173-294`), directly replacing the four-case negative test in which three invalid imports were accepted before the rewrite (`/Users/bozhidardenev/tmp/rep-key-comprehensive-review-consolidated-2026-08-24.md:263-274`). The CI artifact shard builds web, worker, AI, Google and compatibility outputs (`.github/workflows/ci.yml:269-374`); the Docker job builds and scans the ten runtime/CI images (`.github/workflows/ci.yml:399-743`). AI bundle verifiers are also executed inside their Dockerfiles (`Dockerfile.ai-egress-gateway:23-25`; `Dockerfile.ai-execution-admission:20-21`), not orphan scripts.

**Why it matters.** These controls answer executable questions about code that can ship; they materially fix OPS-01..04/OPS-06 rather than merely documenting them.

**Recommendation.** Keep these gates on every PR/main run; add or remove fixture classes only when the actual architecture/artifact boundary changes.

**Cost/risk of the fix.** Already paid. Boundary proof costs 4.63s locally; the ten-image Docker job cost 549s but ran off the critical `check` path in the measured workflow.

### G-A02 The check split is a measured, coverage-neutral latency win

**Evidence.** Commit `dc1fc97e` split one serial job into `static`, `test-unit`, `test-integration`, and `artifacts`, with stable aggregate `check` (`.github/workflows/ci.yml:26-388`). Baseline run `33675157116` spent 1,110s in `check`; split run `33680075174` spent 330s, 369s, 324s, and 91s in the four shards plus 3s in the aggregate. Thus aggregate wall is about $\max(330,369,324,91)+3=372$s, down 66.5%; runner compute is 1,117s, up 0.6%. Current `gate-wiring.test.ts` checks occurrence counts across the whole workflow rather than requiring commands in one named job (`src/shared/governance/gate-wiring.test.ts:85-112`); `pnpm exec vitest run src/shared/governance/gate-wiring.test.ts --project unit` passed 19/19 in 1.25s (8.05s process wall).

**Why it matters.** It answers issue #375 with evidence: coverage was not the cost; serialization was. No correctness gate needs deferral to shorten the loop.

**Recommendation.** Keep the four shards and stable aggregate. Preserve step-level logs when optimizing E2E; do not rejoin shards or defer compatibility/image scans for an illusory wall saving.

**Cost/risk of the fix.** Near-zero compute growth. Risk is topology-test coupling; current occurrence-based invariant is appropriately narrower than the failed job-layout assertion.

### G-A03 Main protection and immutable-SHA preflight are real

**Evidence.** Live GitHub API readback on 2026-09-02 returned required contexts `check`, `docker`, `e2e`, `secrets`, `audit`, with force-push/deletion disabled and linear history required. Release Images binds `target_sha` to a main commit and reads CI conclusions before signing (`.github/workflows/release-images.yml:43-98`). This reverses the pre-review state where branch protection was absent and working-tree deployment undermined provenance (`/Users/bozhidardenev/tmp/rep-key-comprehensive-review-consolidated-2026-08-24.md:477-483`).

**Why it matters.** A merge and a release now have mechanical SHA identity rather than relying on operator memory.

**Recommendation.** Retain the stable `check` aggregate, but generate both required checks and release prerequisites from one manifest as recommended in G-S01.

**Cost/risk of the fix.** Low; changing status names without coordinated branch-protection migration would block all merges, so preserve the aggregate name.

## What is genuinely good

### G-G01 Expensive gates have caught real defect classes

**Evidence.** `git log --all --since=2026-08-19 --oneline --extended-regexp --grep=…` returned: `2ed0e536` (runtime contract tripwire), `bba29980`/`915bdadc`/`6adf0719` (real CodeQL fixes), `5ab0e86f` (Alpine CVE), `e0798c39` (three component defects and one race), `d0f91079`/`d75f9359`/`e40fd754` (Fallow backlog contraction), `6472c91e` (restored Storybook plays/fixture drift), and `790ea6b5` (one bad review date taking down a page). The completion plan independently records 13 files forced through changed-code evidence and 344 Fallow findings, including ~83 dead exports and ~236 complexity findings (`docs/program-completion-plan-2026-08-29.md:73-104`).

**Why it matters.** Type/coverage, SAST, artifact, container, component, Storybook and critical E2E controls protect different failure classes. This is the strongest reason not to “optimize” by deleting the suite.

**Recommendation.** Protect the 55 essential and 43 useful rows in the ledger below; optimize setup and topology, not questions.

**Cost/risk of the fix.** No fix required. Removing these controls would reopen demonstrated classes, not hypothetical ones.

### G-G02 Docker assurance matches the actual image surface

**Evidence.** On run `33680075174`, ten image builds totaled 180s, one smoke step 16s, ten SBOMs plus upload 104s, eight release-image scans 190s, and two CI-only scans 35s (`.github/workflows/ci.yml:399-743`). SAFE-04 explicitly requires SBOM/scan/provenance for every promoted image (`docs/comprehensive-beta-implementation-program-2026-08-25.md:400-412`).

**Why it matters.** The prior mismatch—five builds and only three scans—is gone. Every byte-bearing image family receives the same vulnerability evidence.

**Recommendation.** Keep all ten scans on the push path while Docker remains non-critical; bind their digests to release promotion rather than merely printing them.

**Cost/risk of the fix.** 549s runner wall, but only 0s added to the measured critical path because E2E/check were slower and parallel.

### G-G03 The standards matrix distinguishes evidence, exceptions, and N/A

**Evidence.** The 17×11 test pins exactly 43 accepted exceptions, 120 evidenced cells, 24 not-applicable cells, and zero unresolved (`src/shared/governance/context-standards-matrix.test.ts:77-98`). The model explicitly says “evidenced” is a repository fact rather than blanket release closure (`src/shared/governance/context-standards-matrix.ts:3-10`).

**Why it matters.** This is a useful anti-overclaiming model and satisfies the plan better than a single “standards compliant” badge.

**Recommendation.** Keep the three-state matrix, fix temporal enforcement, and delete universals whose exception rate proves they are not standards.

**Cost/risk of the fix.** Low; deleting two low-leverage dimensions reduces rather than increases ongoing cost.

## What should be improved

### G-I01 Current HEAD is not yet evidence-grade green (medium)

**Evidence.** Remote split run `33680075174` failed after 1,301 files/12,706 unit tests because the old governance test hard-coded one `check` job; current commit `3f76a99c` fixes that and the focused 19-test file passes locally. The same remote run failed Portal critical E2E twice: expected scan counts 8 then 9, received 7 then 8 at `e2e/critical/guest-portal.spec.ts:353`; the Inbox handling-cycle test timed out once and passed on retry, so `--fail-on-flaky-tests` would also have rejected it (`.github/workflows/ci.yml:839-959`). The plan requires current gates green without retry (`docs/comprehensive-beta-implementation-program-2026-08-25.md:423-429`) and forbids retry-to-green (`:1211-1220`).

**Why it matters.** The split itself is fixed, but the product metric failure blocks a real Portal analytics/goal contract and current HEAD has no complete run.

**Recommendation.** Diagnose the missing scan producer/deduplication path and the Inbox button race; rerun the complete current SHA once. Do not relax the assertions or retry policy.

**Cost/risk of the fix.** Bounded product/test diagnosis. Risk is mistaking a deterministic one-count deficit for timing and papering it over with a longer poll.

### G-I02 The repository has three incompatible meanings of “required” (medium)

**Evidence.** Live branch protection requires five contexts: `check`, `docker`, `e2e`, `secrets`, `audit`. Release preflight requires seven differently named jobs—`check`, `docker`, `secrets`, `storybook`, `storybook-test`, `e2e`, `beta-acceptance`—but not Fallow `audit`, CodeQL, or simulation (`.github/workflows/release-images.yml:43-98`). Gate F then validates an input-provided `jobs` array and requires only that at least one row is labeled required, rather than comparing canonical names (`src/shared/release/live-evidence/clean-ci-run.ts:31-100`). REL-01 says the exact executable list lives in CI and the release manifest (`docs/comprehensive-beta-implementation-program-2026-08-25.md:1211-1222`).

**Why it matters.** A SHA can be mergeable, fail release preflight, and still satisfy a fabricated clean-CI evidence object. “Green” depends on which authority is asked.

**Recommendation.** Define one typed/generated required-check manifest. Generate workflow aggregate requirements, release preflight names, branch-protection drift validation, and Gate F clean-CI validation from it. Include Fallow, CodeQL, and path-relevant simulation explicitly or record them as non-required—never omit silently.

**Cost/risk of the fix.** Medium, mainly safe migration of required context names. Roll out additive checks first, update protection, then remove old names.

### G-I03 Standards exceptions are honest today but do not actually expire (medium)

**Evidence.** `jq` audit returned 43 entries, 0 unowned and 0 expired as of 2026-09-02; dimensions are errors 7, files 17, repositories 3, tags 1, triple 15. Every entry was reviewed 2026-08-28 and expires 2027-02-28; register review is 2026-09-30. The test checks only `nextReviewAt > reviewedAt` and `expiresAt > reviewedAt`, never either date against `new Date()`/today, and `compensatingCheck` is merely a non-empty string (`src/shared/governance/context-standards-authority.test.ts:19-53,134-183`). Therefore every row will remain green after expiry.

**Why it matters.** The plan explicitly requires owned/expiring exceptions and says to retire ceremony (`docs/comprehensive-beta-implementation-program-2026-08-25.md:1146-1155`). “Expiry” that never changes a decision is metadata, not a control.

**Recommendation.** Make the gate accept a clock and fail when `nextReviewAt < today` or any `expiresAt < today`; map each `compensatingCheck` to an executable gate ID. Retain the 11 bounded tag/error/repository exceptions while migrating them. Delete the universal `triple` and `files` standards and their 32 exception rows rather than churning 15/17 and 17/17 contexts.

**Cost/risk of the fix.** Low for clock enforcement; low-to-medium documentation/test contraction. No application behavior changes are needed to retire low-leverage maintainability universals.

### G-I04 E2E setup is now the critical path; keep coverage and remove duplicated work (medium)

**Evidence.** Split run `33680075174` spent 44s installing browsers, 194s starting the stack, 13s smoking it again, and 424s reaching the critical failure. `up()` already invokes `smoke()` (`scripts/local-stack/stack.ts:1896-1921`), so the explicit CI smoke repeats the same check. Issue #375's measured resolution likewise found compatibility to be only 59s and concluded no gate should move off push.

**Why it matters.** Deferring image scans or browser compatibility would reduce assurance without reducing wall; the actual avoidable cost is setup duplication/contention.

**Recommendation.** Delete only the second smoke invocation (G056), share/cache dependency layers across local Compose images, and overlap independent browser installation with stack construction only if separate logs remain legible. Keep critical/full/compatibility suites on PR and main.

**Cost/risk of the fix.** Immediate 13s saving, larger 40–135s cache/layer opportunity. Parallel setup risks poorer diagnostics unless logs are separated.

### G-I05 Protection exists but does not meet the high-risk-review contract (medium)

**Evidence.** Live protection readback returned `strict: false`, `enforce_admins: false`, and no `required_pull_request_reviews`; only five status contexts and linear history are enforced. `.github/CODEOWNERS` can route reviewers but cannot require one; root `/CODEOWNERS` is ignored when `.github/CODEOWNERS` exists. **Cost/risk of the fix.** Low configuration cost; risk is lockout if status-name migration is not staged.

## What needs substantial change

### G-S01 The central gate policy is an unused, incomplete second authority (high)

**Evidence.** `GATE_POLICY` self-describes as seeded/incomplete and contains eight rows (`src/shared/release/gate-policy.ts:79-176`), i.e. 6.9% of the 116-row inventory. Its validator checks duplicate IDs, correctness posture and non-empty rationale but not source location, command reachability, completeness, or freshness (`src/shared/release/gate-policy.ts:225-256`). `pnpm gate --list` reports six armed/two dormant, while search across `.github` and `.husky` finds zero `pnpm gate` consumers. The CLI itself correctly rejects unknown IDs (`scripts/ci/gate.ts:1-18,48-72,111-153`), but nothing calls it. Inventory prose still says “7 of 106,” demonstrating drift (`docs/operations/gate-inventory-2026-08-31.md:21-47`).

**Why it matters.** Issue #372 claims posture is a single switch and the CLI bridges YAML/Husky, but current automation bypasses it. Operators can receive a green policy answer about 8 rows while 108 live/inventoried mechanisms follow unrelated triggers.

**Recommendation.** Do not hand-maintain 116 policy rows beside YAML. Make one compact manifest authoritative for only decision-bearing top-level gates, generate workflow conditions and the audit table from it, and fail CI on discovered-but-unregistered executable gates. Delete `GATE_POLICY`/`pnpm gate` if generation is not adopted; an unused registry is worse than direct YAML.

**Cost/risk of the fix.** Medium redesign with high payoff. Migration risk is silent gate loss; require generated-diff and unknown-command negatives before cutover.

### G-S02 Gate F is unreachable and structurally impossible for the actual beta (high)

**Evidence.** Gate F uses a fixed 18-ID array (`src/shared/release/gate-f-evidence.ts:46-65,248-273`) and never consults `GATE_POLICY`. The only top-level command is `package.json:83`; no workflow calls it, and Release Images has zero observed runs. Nine live-evidence importers call a common validator that requires `capturedBy !== attestedBy` for every evidence type (`src/shared/release/live-evidence/common.ts:55-58,118-127`). Gate policy says the latter two are dormant at closed beta, but the fixed list still requires them. The referenced GitHub environment `release-signing` has no live environment object; the two existing environments have no protection rules, so the first run would auto-create an unprotected environment (`.github/workflows/release-images.yml:103,281`).

**Why it matters.** The one-person/six-property beta cannot truthfully produce the bundle, while the deployed product continues without it. That is exactly the plan's prohibited split between operational reality and governance evidence, and it blocks the planned external cohort rather than making it safer.

**Recommendation.** Replace the fixed list with the generated posture manifest. At closed beta, allow one actor to capture and attest ordinary machine evidence, reserving distinct review for the high-risk review category via fresh-context review + founder sign-off. Arm cohort/counsel gates only for external/open-beta activation. Create a protected signing environment only when a distinct eligible reviewer exists; until then remove the false protection claim and make the signing step's solo authority explicit.

**Cost/risk of the fix.** Medium-to-high because schemas/importers and release process change together. Risk of weakening evidence is controlled by keeping machine provenance/immutable SHA checks unconditional and changing only human-separation requirements.

### G-S03 Manual catalogues combine projection, discovery, and runtime authorization (high)

**Evidence.** The entry catalogue is 6,348 lines and calls itself canonical while permitting `canonicalOnly` rows (`src/shared/governance/entry-point-catalogue.ts:1-30,39-105`). Its tests discover source declarations and operator commands (`src/shared/governance/entry-point-catalogue.test.ts:310-429`), but registration marks routes/operators direct when a file exists (`src/shared/governance/entry-point-catalogue.ts:461-489,583-612,1348-1375`), not when a process invokes them. Job retry/timeout/readiness likewise derive from the event/job catalogue (`src/shared/jobs/job-policy.ts:1-22,64-97`; `src/shared/jobs/readiness.ts:1-19,55-97`). Focused current tests pass 56/56 in 12.68s, which proves internal consistency—not metadata truth. Of 109 events, 47 are marked `denied_dark`; 41 of those are Portal read/write even though the live capability record says Portal read/write/public/guest are ON (`docs/operations/capability-state-2026-09-02.md:43-92`; `src/shared/auth/beta-capabilities.ts:642-660`).

**Why it matters.** A manually wrong row can alter authorization, retry or readiness while the same hand-authored catalogue's test stays green. **Recommendation.** Make runtime registration the authority: route/job/consumer builders register typed descriptors; boot emits the actual graph; generated catalogues/docs compare to it. **Cost/risk of the fix.** High but bounded to governance/runtime registration seams. Migrate one entry kind at a time with dual comparison, then delete manual rows; avoid a flag-day rewrite of 542 entries.

#### Explicit answer to issue #375: what stays on every push

Keep every existing correctness-bearing PR/main job: the four `check` shards and aggregate, Docker build/smoke/SBOM/Grype, secrets, critical/full/compatibility E2E, Storybook build/tests, CodeQL and Fallow. The measured split already cuts `check` wall 66.5% without deferral; Docker is not the pole, and compatibility is ~57s. Keep beta acceptance main/manual/labeled only. Add simulation on relevant main pushes and bind CodeQL/simulation disposition into release preflight. Delete local pre-push duplicates and the second E2E smoke; optimize shared image layers/setup next. This follows the plan's “no retry/skipped gate” requirement (`docs/comprehensive-beta-implementation-program-2026-08-25.md:1211-1222`) and the measured resolution in issue #375.

#### Explicit answer to issue #374: what automatically contradicts `closed-beta`

A single persisted fact is sufficient: **an active application principal other than the declared owner can authenticate into any beta organization, or a second active organization exists**. Check it transactionally when accepting an invitation, activating membership, or creating an organization; refuse only that widening operation with an actionable “change `CURRENT_RELEASE_POSTURE` first” error. Also evaluate the invariant at web/worker boot and continuously in readiness/alerting so out-of-band database changes cannot hide; CI cannot prove production audience state. A connected GBP is _not_ an audience signal—it already introduces reviewer data subjects even for one operator—and an anonymous route leaking tenant data is a security defect at every posture, not a reason to rename posture (issue #371's correction; `review.schema.ts:72-73`). Before allowing the posture change, the generated gate manifest must show open-beta gates armed. `[UNVERIFIED]` current production needs a query for active principals/memberships, organizations, and published Portal tokens; capability ON alone does not prove a second participant.

## Opinion (clearly separated, short)

The strongest engineering choice in this rewrite is the boring one: split independent work and keep the questions. The weakest is treating hand-authored catalogues, evidence bundles, and prose inventories as additional authorities. For a one-tenant beta, one generated gate manifest plus executable runtime registration would be safer and materially smaller than three mutually inconsistent governance systems.
