# Security posture — state of the app, 2026-09-02

## Verdict

The security _machinery_ is real, singular, and reachable — and the security _paperwork_ at the repository root is a pre-rewrite fossil that contradicts it. Tenant isolation has exactly one enforcement mechanism (`resolveTenantContext` → `requireExecutionAllowed` → per-permission `scopeForPermission` → one grant lookup); I sampled 25 server functions across 11 contexts and found zero reachable isolation bypass, with property scope derived from the governing permission everywhere, never from a role comparison or a literal boolean. The public Portal/Guest edge is the strongest surface in the repository: exact origin pinning, a scope-bound signed session, constant-time CSRF, three-layer rate limiting (session / network+Portal Redis / durable Postgres pressure), non-enumerating 404s, `private, no-store` applied _inside the validator_ so malformed input gets the same privacy policy, and a honeypot decoy path. AI provider minimization is a genuine code path plus a closed `.strict()` schema in which private ratings, private feedback, contact, Inbox notes and manager text are _not representable_ — not a doc promise. mTLS peer identity is real X.509 validation (`socket.authorized` + exact SAN + exact EKU OID set), not header trust. Against that, `SECURITY-AUDIT-REPORT.md` sits at the repository root dated 2026-05-22 asserting P1 findings against three files that no longer exist and an authorization model that was replaced wholesale, and `docs/SECURITY_ONBOARDING.md` §4.1/§7 tell an operator that email verification is hard-disabled and "anyone can register with any email address" — both false. I found **no reachable-today exploitable defect**; every finding below is honesty, latent-contract, or proportionality.

### The single enforcement mechanism, and why it is not bypassable

There is exactly one property-access source. `ExecutionPolicy.listAccessiblePropertyIds` (`identity/infrastructure/policy-store-init.ts:142-145`) and `StaffPublicApi.getAccessiblePropertyIds` (`contexts/staff/build.ts:81-95`) both resolve to the same `createGrantAccessLookup` (`policy-store-init.ts:118`) — the staff API is a thin `orgWide ? null : accessiblePropertyLookup(...)` wrapper with an in-source comment saying exactly that ("the GRANT lookup decides — empty array means no grants, which downstream helpers treat as deny, never organization-wide allow"). No second grant-table read appears anywhere in the sample.

Fail-closed properties verified in source, not in docs:

- `propertyScopeDecision` (`execution-policy.ts:364-388`): `scope === 'none'` → `scope_denied`; grant-lookup throw → `policy_unavailable`; empty grant list → `scope_denied`. Never "org-wide allow".
- `resolveBuiltInAuthorization` fails closed on custom roles; `resolveDynamicAuthorization` catches and `throwAuthError('authorization_unavailable')` (`tenant-resolver.ts:257-282`).
- `versionedEntryIsFresh` (`tenant-resolver.ts:150-152`): a _failed_ `permission_version` read is treated as stale, not fresh.
- `decideTenantCacheAction` (`tenant-resolver.ts:131-141`): an entry without a version proof is never served across requests — "membership removal and role downgrade must be visible on the next command, not after the cache TTL".
- `buildAuthContext` `Object.freeze`s the shared cached context so a caller cannot poison another request's authority (`tenant-resolver.ts:309-317`).
- Beta role gate: `isBetaInteractiveMemberRoleToken(member.role)` → `beta_role_inactive` (`tenant-resolver.ts:427-436`).
- `system` principals deny as `unsupported_principal` in the interactive policy (`execution-policy.ts:596+`); operator principals deny as `operator_not_registered` unless present in `OPS_OPERATOR_IDENTITIES` (`execution-policy.ts:508-511`, bound at `policy-store-init.ts:150`; absent allowlist = every operator command denies).
- Better Auth org-lifecycle writes are refused twice: HTTP path-pinned block list (`routes/api/auth/$.ts:34-44`) and provider hooks `beforeAcceptInvitation | beforeRemoveMember | beforeUpdateMemberRole | beforeDeleteOrganization` → `denyRawOrganizationLifecycleWrite` (`auth.ts:36-42,186-191`).

### The AI egress path, traced end to end

One request — `generateReplySuggestionFn` — with the minimization step named:

1. `contexts/ai/server/reply-suggestion.ts:36` — `resolveTenantContext(headers)`. Org identity comes from the session, never the payload (the DTO at `:18-28` is `.strict()` and carries only `reviewId`, `tone`, `targetLanguage`, `idempotencyKey`).
2. `:41-45` — `reviewPublicApi.aiReviewSource.readCurrentSource({ organizationId: ctx.organizationId, reviewId })`. Tenant predicate at `review.repository.ts:180`: `and(eq(reviews.id, id), eq(reviews.organizationId, organizationId))`.
3. `:53-57` — `requireExecutionAllowed({ action:'ai.reply.generate', propertyId: current.source.propertyId })` → capability `ai.generate_reply` (ON per `capability-state-2026-09-02.md:48`) → permission → grant scope → **Merchant AI consent fence** (`execution-policy.ts:113-140`): property-subject only, UUIDv1-8 lineage id, `capabilityEpoch ≥ 1`, `authorizedSourceEpoch ≥ 0`, `stateVersion ≥ 1`, 64-hex notice digest, non-empty runtime profile version — all six must be well-formed or the selector is not even considered bound, and an unbound selector short-circuits to `consent_required` (`execution-policy.ts:394-410`).
4. `contexts/ai/application/use-cases/generate-reply-suggestion.ts:256-262` — `reviewSources.readForAi({organizationId, propertyId, reviewId})`, in parallel with `authorization.readMerchantAuthorization` and `processingProfiles.readForAi`.
5. **THE MINIMIZATION STEP — `src/shared/ai-review-source-contract.ts:218-256`, `minimizeReviewerIdentity()`**, invoked from `computeAiReviewSourceProvenance` (`review/application/ai-review-source.ts:34`). The reviewer display name is Unicode-case-folded via the generated fold table, located in the review text with exact scalar-boundary mapping, and replaced with the literal `[PERSON]`. Pre-existing `[PERSON]/[CONTACT]/[ADDRESS]/[FINANCIAL]/[IDENTIFIER]/[SECRET]` tokens in guest-authored text are escaped to `{#1#}…{#6#}` (`:74-80,213-218`) so a review cannot forge a placeholder. Input is NFKC-normalized with control/bidi scalars stripped (`:139-144`). The canonical encoding then carries **only** `text, rating, languageCode, reviewedAtEpochMillis` (`encodeSource`, `:266-296`) — `reviewerDisplayName` has no slot in the wire format at all.
6. `review.repository.ts:251-264` — the recomputed canonical digest is `timingSafeEqual`-compared against the persisted `ai_source_digest`; a mismatch returns `policy_unavailable` and **no provider call happens**. SQL-level eligibility (`review.repository.ts:145-168`) additionally NULLs text/language/reviewer when content is expired (`content_expires_at > captured.now`) or over the raw byte budget, and the read runs inside `db.transaction` with the tenant predicate `organization_id = $ AND property_id = $::uuid AND id = $::uuid`.

## What is genuinely good

### G1 — The public Guest edge is load-bearing and correct

`contexts/guest/server/public.ts:56-99` `resolveBoundSession` is the single gate for every public mutation, and its ordering is right:

1. portal resolution by token (`:69-74`), any failure → `denyWithoutEnumeration()`;
2. **exact `Origin` equality** against `guestPublicRuntime.expectedOrigin` (`:80-83`) — a missing `Origin` is `null !== expected`, so `curl` fails closed;
3. signed cookie verification **bound to `{org, property, portal}`** (`guest-session.ts:186-193`);
4. constant-time CSRF (`guest-session.ts:206-212`);
5. `decidePublicExecution` with declared consent assertions and required consents (`:88-96`).

Every failure funnels into `denyWithoutEnumeration()` (`public.ts:50-55`) returning an identical 404, and `lifecycleFailure` (`:101-119`) explicitly maps `response_not_found | response_unavailable | media_not_found` to that same 404, so an attacker cannot distinguish "no such portal" from "portal denied" from "no such response". `getPublicPortal` (`guest-scans.ts:252-262`) additionally resolves the guest-response capability decision **only after** the `portal.public_read` deny has thrown, with an in-source comment stating why — a denied portal and a missing one stay indistinguishable.

Locale handling has a subtle correctness win worth protecting: the cookie's signed locale is only honoured **after** the token has established the exact `{org, property, portal}` scope and the cookie has been verified against it, then the portal is re-resolved (`guest-scans.ts:258-273`) — "a signed preference from another Portal can never influence this response".

Why this is load-bearing: it is the only internet-reachable unauthenticated write surface in the product, and the one place where a mistake is silently exploitable by anyone with a QR code. Do not "simplify" `resolveBoundSession` into per-handler checks.

### SEC-I4 — No static gate prevents a _new_ repository query from omitting the tenant predicate

**Verdict: IMPROVE. Severity: medium.**

**Evidence.** Tenant predicates are verified per-repository by real-Postgres two-org tests (84 files), and the authorization layer is gated by architecture tests, but there is no assertion that _every_ query in `src/contexts/*/infrastructure/repositories/**` carries an `organizationId` conjunct or an explicit, reviewed exemption. `src/shared/architecture/` contains `tenant-cache-transition-ownership.test.ts`, `observability-canary.test.ts`, `privacy-exfiltration-canary.test.ts`, `security-headers-wiring.test.ts`, `composition-container-boundary.test.ts`, `context-acceptance-matrix.test.ts` — no tenant-predicate canary. The 2026-05 audit's own T1/T2/T4/T5 rows show this exemption class is real and recurring (`findByGbpPlaceId`, `deleteAllExpired`, `findAll*`, `resolveLinkById`), and nothing today records the _current_ exemption list. `context-acceptance-matrix.test.ts:180-181` shows the project already knows how to record a reviewed exemption in prose ("WATCH (owner Property): legacy leaderboard_snapshots rows carry no organization_id …") — but only for one file, not as a systematic map.

**Why it matters.** The isolation guarantee is currently upheld by 84 tests written by whoever remembered to write them. `src/contexts` is 400k+ non-test lines across 17 contexts, with single files as large as `inbox-command-store.ts` (3,392 lines). The next repository method added without a two-org test is silently unprotected, and `§3.8.7` requires "no known reachable High defect in tenant isolation" — a claim that gets harder to hold each quarter without a mechanical floor.

**Recommendation.** Add one architecture test that AST-walks `contexts/*/infrastructure/repositories/**/*.ts`, collects every drizzle `.where(...)` / `sql\`\``targeting a tenant-owned table, and requires either an`organizationId`/`organization_id`conjunct or membership in an explicit`TENANT_PREDICATE_EXEMPTIONS`map carrying owner + reason — exactly the shape`src/shared/db/schema/db-only-constructs.ts:757-800`already uses for DB-only constructs, so the pattern is established and reviewable. Seed the map from the current true exemptions (public capability-token lookups such as`resolveLinkById`, system batch sweeps such as `findAllExpiredBefore`).

**Cost/risk.** ~150 lines of test plus one exemption map. Risk: initial false positives on raw-SQL repositories; scope the first version to drizzle query-builder calls and widen later. This is the single highest-leverage addition on this axis.

### SEC-I5 — Custom roles are fenced three ways but still _enabled_ in the provider

**Verdict: IMPROVE. Severity: low.**

**Evidence.** `§3.1.3` — "Runtime custom roles are off." Fences in place: `identity.custom_roles` is a BLOCKED capability (OFF per `capability-state-2026-09-02.md:55`); the raw routes `/organization/create-role|update-role|delete-role` are refused at the HTTP boundary (`routes/api/auth/$.ts:34-36`); the app-owned server functions require the blocked capability (`organizations.roles.ts:49-52,74-77,98-101`); and role _resolution_ is separately gated by `ENABLE_CUSTOM_ROLES` (`tenant-resolver.ts:293-297`). But `src/shared/auth/auth.ts:167-169` still configures `dynamicAccessControl: { enabled: true }`, with a comment citing "ADR 0001 Phase 4" and "Custom-role admin UI is still TBD" — pre-rewrite framing.

**Why it matters.** Defense in depth is correct here, but the innermost layer is set to the wrong default. `routes/api/auth/$.ts:11-18` warns explicitly that the block list is **path-pinned** to better-auth 1.6.23 and "a bump can rename a route and silently narrow this refusal to nothing". The blocked-capability check guards RepKey's own server functions, not the provider's route table. Turning the provider feature off removes the class rather than listing its instances.

**Recommendation.** Set `dynamicAccessControl: { enabled: false }` and rewrite the comment to cite §3.1.3 rather than ADR 0001 Phase 4. Keep the `organizationRole` table — dormant schema is explicitly permitted by §3.1.3. The colocated version-pin test (`routes/api/auth/-$.test.ts`) already asserts the installed better-auth version and will keep guarding the route list.

**Cost/risk.** One-line configuration change plus verifying no test depends on the provider accepting role writes. Low.

### SEC-I6 — The CN peer-identity fallback survives in `internal-mtls.ts`

**Verdict: IMPROVE. Severity: low.**

**Evidence.** `SAFE-04` §1: "Require exact SPIFFE-style SAN and EKU peer identity; **remove CN fallback**." `services/internal-mtls.ts:79-89` still contains it:

```ts
const socket = request.socket as TLSSocket
if (!socket.authorized) return null
const certificate = socket.getPeerCertificate(true)
if (resolver) return resolver(certificate)
const commonName = certificate.subject?.CN
return typeof commonName === 'string' && /^[A-Za-z0-9._:@/-]{1,255}$/.test(commonName)
  ? commonName
  : null
```

and `resolvePeerIdentity` is **optional** in the server options (`:379`), with `:446` branching on `if (input.resolvePeerIdentity && resolvedPeerIdentity === null)` and `:531` on `(!input.resolvePeerIdentity || resolvedPeerIdentity !== null)`.

Mitigating: every production listener supplies an exact resolver — `services/ai-execution-admission/index.ts:103-106`, `services/ai-egress-gateway/bootstrap.ts:92-100`, `services/google-peer-identities.ts:31-50` — the resolver itself is strict (exact sorted SAN list equality plus exact EKU OID set equality, `internal-mtls.ts:194-201`), the listener is `requestCert: true, rejectUnauthorized: true, minVersion: 'TLSv1.3'` (`:422-424`), and the negative matrix exists (`internal-mtls.test.ts:188` — "rejects extra SANs, wrong URI, missing/wrong/extra EKUs, and CN fallback"). So this is latent, not reachable: exploiting it would still require a certificate signed by the internal CA.

**Why it matters.** The package's definition of done says the fallback is gone; it is not. A new sidecar added without `resolvePeerIdentity` silently degrades to "any certificate our CA signed, identified by CN" with no type error and no gate failure — precisely the "declared vs. actual" gap this program exists to close.

**Recommendation.** Make `resolvePeerIdentity` **required** in the server options type (`internal-mtls.ts:379`), delete the CN branch at `:86-88`, and let `peerIdentity()` return `resolver(certificate)` unconditionally after the `socket.authorized` check. The compiler then enumerates every call site; all production ones already pass a resolver. Add the assertion to `services/sidecar-entrypoint-wiring.test.ts`.

**Cost/risk.** ~15 lines. Any test constructing a server without a resolver breaks — that is the point.

### SEC-I7 — Three small ordering/labelling nits on otherwise-correct paths

**Verdict: IMPROVE. Severity: low.**

1. **In-tenant existence oracle.** `contexts/ai/server/reply-suggestion.ts:41-52` performs the org-scoped review read **before** `requireExecutionAllowed` at `:53`, so a manager without a grant on property P distinguishes "review exists in my org" (403) from "does not exist" (404). Contained to one tenant, no cross-tenant read. Fix: read only `propertyId` first and hoist the scope check, or return the same 404 for both.
2. **Scope enforced in a different layer, silently.** `contexts/activity/server/activity.ts:45` is the only sampled server function whose property scope lives in the query layer rather than at `requireExecutionAllowed`. It is correct and fail-closed (`get-activity-timeline.ts:37-51`, `list-recent-activity.ts:23`), but the divergence is invisible at the call site. Fix: one comment naming the layer that owns the scope.
3. **Guest cookie prefix.** `rk_guest_session` (`guest/domain/guest-session.ts:33`) carries no `__Secure-` prefix. `__Host-` is inapplicable (it forbids a `Path` other than `/`, and this cookie is deliberately path-scoped to `/p/`), but `__Secure-` is applicable and would prevent a non-TLS sibling origin from overwriting it. The HMAC plus `{org, property, portal}` scope binding already makes an overwrite useless, so this is cosmetic hardening only. Note the contrast with the Better Auth session cookie, where `tenantCacheKey` (`tenant-resolver.ts:90-100`) explicitly handles the `__Secure-` prefix and documents why misalignment would either inert the cache or alias two secure sessions — the prefix discipline exists on the authenticated side and simply was not carried to the guest side.

## Opinion

Three points, clearly separated from the findings above.

**The security code is materially better than the security documentation, and the documentation is what strangers read first.** If I could make exactly one change on this axis it would not touch a `.ts` file: delete `SECURITY-AUDIT-REPORT.md` and re-date the threat model. The implementation earned a good verdict; the root of the repository currently disagrees with it in writing, and under this program's own precedence rules that disagreement is itself the defect.

**`SEC-I4` is the finding I would fund first among the code-adjacent ones.** Eighty-four two-org tests is genuinely good coverage, but coverage achieved by discipline decays; coverage achieved by a gate does not. The project already has the exact pattern it needs (`db-only-constructs.ts`'s owner/reason/source exemption registry) and has demonstrated it can write AST-level architecture tests. A tenant-predicate canary with an explicit exemption map converts the isolation guarantee from "we remembered" to "the build refuses" — and it is the guarantee whose failure ends the beta.

**The `ExecutionPolicy` shape is right and I would not touch it, but I would make the decision audit deny-biased.** Writing a row for every allow at a scale of one tenant produces a table whose signal-to-noise ratio _falls_ as usage rises; deny rows plus sampled or operator-only allow rows carry essentially the same forensic value at a fraction of the write volume. That is a tuning opinion, not a defect — the current behavior is correct, the audit sink is content-free and error-tolerant by design, and the plan specifies no sampling policy.
