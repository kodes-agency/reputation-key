## What the Sept 2 review already found

- Unit setup costs as much as tests; 1,302 files each load `src/test-setup.ts` through four forks; 317 files have ≤2 declarations (`review/2026-09-02-state-of-the-app/TEST.md:178-182`).
- The `revision_conflict` product bug was papered over with a 45-second harness wait (`TEST.md:220-226`) — **now closed**: commit `fbc87992` recovers the conflict in `src/components/inbox/use-inbox-detail-queries.ts:65-107` and `waitForInboxItemSettled` has zero callers.
- "Deployed critical journeys" are six anonymous GET probes wrapped in a 729-line runner (`TEST.md:200-206`).
- The quality gate checks syntax smells, not assertion meaning; concrete `typeof`/source-substring/`data-slot` examples (`TEST.md:186-194`); a prune list totalling ≈2,400–2,500 lines (`TEST.md:243-256`).
- Coverage excludes the integration project and is a unit-only number (`TEST.md:158-164`); Storybook judged "proportionate and fast; keep" (`TEST.md:271`).

## What it missed or got wrong under the one-developer lens

- **Its deletion target is 0.7% of the estate** (`TEST.md:256`, ≈2,450 of 345,182 lines). The measured cost centre is not mock twins in product contexts; it is 236 governance/harness files that are 13% of lines and 77% of unit execution seconds.
- **It recommended preserving the coverage ratchet and merging integration into it** (`TEST.md:49,162`). The ratchet already costs a complete second unit execution per PR (`ci.yml:115-145`, 344s) and its own header records what it has ever caught: a coverage _percentage_ falling (`scripts/check-coverage.mjs:50-60`), never a defect.
- **It did not name the files that dominate runtime.** `one-container-per-process.test.ts` spawns web/worker/sidecar/simulation composition roots (`src/shared/testing/process-fixtures/one-container-per-process.test.ts:18-23`) — 155s to prove eight facts about a topology that is already decided to be collapsed. `entry-point-catalogue.test.ts` exists to keep a 6,348-line hand-written catalogue consistent with source text, and it timed out on this laptop (`entry-point-catalogue.test.ts:1264`).
- **It did not look at CI outcome history.** Main is red half the time and every recent failure is e2e or beta-acceptance infrastructure, none is `test-unit`. For a solo developer that is the tax: a red main that means nothing.
- **It priced Storybook as "keep" without pricing the two-runner design**: `.storybook/main.ts:3-21` keeps both `@storybook/test-runner` and a Vitest browser project because `@storybook/addon-mcp` depends on the latter; the newest flake-register entry is a storybook-test timeout (`docs/operations/e2e-flake-register.md:59`); the MCP server failed to connect this session.
- **It proposed adding** three tracer e2e journeys plus a deployed synthetic-tenant journey at 1–2 weeks each (`TEST.md:204-216`). With one organisation and six properties, the deployed proof is the founder opening the inbox after deploy.
- **Tests of documents.** Four `adr-*-presence.test.ts` files (248 lines) assert English prose in ADR markdown, e.g. `expect(body).toContain('Cross-cell fallback')` (`src/shared/architecture/adr-0048-presence.test.ts:31-38`). 37 test files (10,221 lines) read `docs/`, `CONTEXT.md`, or `.github/workflows`. Not sized by the review.
- **Tests of the developer's laptop.** `src/shared/testing/pinned-runtime.test.ts:132` fails on any Node other than 22.23.2 — it failed here — and `scripts/check-test-quality.mjs:102-107` fences 146 tests on the exact ICU build. A one-developer project should not have a test whose only failure mode is "you upgraded Node".
- **The org-lifecycle/export twin pattern** (32 unit + 32 integration files, 24,381 lines for 12,773 source lines) is absent from the review; the unit halves are type-shape tests (`notification-organization-lifecycle.adapter.test.ts:59-65`: `expect(contributor.context).toBe('notification')`, `toBeTypeOf('function')`).
- **`pnpm test` needs Postgres.** `package.json:34` is bare `vitest run`, which runs both projects; `vitest.config.ts:16-17` claims it scopes to unit. Small, but it is the command a solo dev types.
