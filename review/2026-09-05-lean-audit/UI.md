## What it missed or got wrong under the one-developer lens

- **The bundle budget is green because it measures the wrong thing; every page actually ships ~650 KB gzipped.** `scripts/check-bundle-budget.mjs:57-72` sizes only the single `index-*.js` file and labels `vendor-charts` a lazy chunk (`:16`). Measured: the entry (`index-DPtWgZKv.js`, 88.6 KB gz; it is `src/client.tsx` + `router.tsx` + `routeTree.gen.ts`, per its sourcemap) has 69 direct static imports whose transitive closure is 171 chunks / 628,719 B gz. Three mechanisms: (1) the `vendor-charts` group in `vite.config.ts:396-400` is defined with rolldown's default recursive dependency inclusion, so **`react` and `react-dom` production builds live inside `vendor-charts-*.js`** (its sourcemap lists `react/cjs/react.production.js`, `react-dom/cjs/react-dom.production.js`) and the entry statically imports it — recharts (413 sources, 27 packages) is fetched before the login page can render; (2) `src/routes/_authenticated/inbox/index.tsx:6` imports `inboxSearchSchema` from `#/components/inbox/inbox-page-v2` (which merely re-exports it at `inbox-page-v2.tsx:34` from `inbox-search-schema.ts`), so the schema's static half of the route drags the entire inbox tree — 86 source files, 28 KB gz (`app-shared~index~index~reviews-*.js`) — into the initial graph, while `reviews.tsx:11` already imports the schema module directly; (3) the portals route definitions pull `app-shared~…cho6jgva-*.js` (101 source files, 32 KB gz, including `ui/color-picker.tsx`, the whole portal form, `vendor-dnd` and the Sentry browser SDK) statically. The owner's own budget is <300 KB per app page; the real figure is 2.2× that. `src/shared/config/bundle-budgets.ts` is a second, advisory budget table that nothing but its own test imports.
- **The Staff shell serves a role no one can hold.** Invitations accept only `AccountAdmin | PropertyManager` (`src/contexts/identity/application/dto/invitation.dto.ts:9,21`); the only way to become `Staff` is the fallback `org.role ? … : 'Staff'` at `src/routes/_authenticated.tsx:112`. Behind that fallback: `home.tsx` (113), `features/staff` (1,397 incl. 523 story lines), `layout/staff-sidebar.tsx` (117) + story (65), `staff-property-switcher.tsx` (60), `staff-nav-items.tsx` (34), and `progress.tsx`/`dashboard.tsx` redirects to `/home`. ≈1,800 frontend lines plus three staff-home server functions for a persona §3.1.2 defers. The review said "freeze"; the lean answer is delete.
- **The 150-line rule is manufacturing files, not clarity.** 273 of 452 production component files are under 100 lines (mean 91). The Google import wizard is 35 files / 6 hooks / 3,216 lines for an action each of the six properties performs once; the two routes that mount it duplicate the same nine server-function props verbatim (`import-google/index.tsx:103-111` vs `$importId.tsx:83-97`). `reply-editor.tsx` is a 48-line pass-through whose only work is renaming a prop (`reply-editor.tsx:36`), and `reply-form.tsx:35` exports a component called `ReplyEditorInner`. The review counted files as health ("mostly live"); under one developer they are navigation cost.
- **Whole UI surfaces exist for capabilities that are off or unnecessary for one tenant.** `edit-portal-form.tsx:120-127` renders `HeroImageSection` with full presigned-upload wiring while `portal.upload` is `safety_blocked` (`capability-fate.ts:81-85`); the control is not gated in the component — the guest would click "Upload hero image" (`hero-image-section.tsx:30`) and be refused server-side. The Closure Center (`features/closure` 1,097 + route 103 + test 180 = 1,380 lines) is a self-service org-closure UI for the one AccountAdmin who is the founder's only customer, when `ops:report-organization-lifecycle` already exists. Beta feedback with masked-layout screenshot capture (`features/beta-feedback`, 920 lines) is an in-app ticketing channel for a customer the founder talks to directly.
- **Storybook is the largest single line item in the frontend and is judged only by its output, not its cost.** 15,096 story lines (37% of production component lines), a 1,194-line fake server, two parallel runners (`.storybook/main.ts:3-19` admits the vitest one "feeds no release evidence"), `addon-mcp` for an AI design loop whose sole artefact is one 47-line `design-qa.md` from 2026-08-22 pointing at `~/.codex/...` screenshots, plus 98 s of local build and two CI jobs. The review scored it "G" on EXP-02.9 without pricing it.
- **fallow cannot see frontend dead code** because stories are entry points; the review's manual census (3 dead files) is still the only true signal. `copy-button.tsx`, `property-dashboard-stories-data.ts`, `fleet-overview.stories.fixtures.ts` remain.
- The review's "four availability vocabularies" is now one for dashboards but the goals matrix was left out of `fbc87992` (`goals/goal-results-matrix.tsx` still prints `ready|updating|insufficient|unavailable` itself).

## The three journeys — indirection audit

**Manager: login → inbox → read → reply.** 12 hops from `/login` to a persisted reply: `login.tsx:24` → `_authenticated.tsx:67-171` (session, org, capability set) → `inbox/index.tsx:16-40` builds a 15-function `inboxFns` bundle (`-inbox-fns.ts:24-41`) → `inbox-page-v2.tsx:60` → `use-inbox-page.ts:81,126` → `use-inbox-state.ts:52` (infinite query) → `inbox-detail-content.tsx:35` → `use-inbox-detail.ts:149` → `use-inbox-detail-queries.ts:111` → `reply-editor.tsx:36` (pass-through) → `reply-form.tsx:35` (`ReplyEditorInner`, which value-imports 7 more server functions directly, `reply-form.tsx:6-14`, the documented exception) → `reply-status-view.tsx:26` → `reply-editor-compose.tsx:44` → `use-reply-composer.ts` / `use-reply-suggestion.ts:30` → `contexts/review/server/reply-draft.ts:17`. 22 server functions reachable from one inbox session, 11 hooks, a 4-deep hook stack before the first query, and two wiring conventions (prop bundle vs direct import) in the same tree. The inbox is where the customer lives, so this should be the flattest surface, not the deepest: one `useInbox()` hook owning list+detail, one `ReplyEditor` file, one convention.

**Manager: connect Google → import → see reviews.** 9 hops: `settings/integrations.tsx:42` → `connect-google-button.tsx:31` (`window.location` to Google) → `api/auth/google/callback.ts:75-153` (four admission gates, then redirect) → `import-google/index.tsx:48` (`gateControlledRoute` + role check `-route-access.ts:6-10`) → `google-import-manager.tsx:47,58` (two controllers) → `startImport` → `$importId.tsx:52` remounts the same manager with the same nine props → `use-google-import-progress-query.ts:39` polls with `refetchInterval`, while sibling queries use `usePageVisibleAndFocused` (`use-google-import-queries.ts:144`) — two polling policies in one wizard → `reviews.tsx:50` renders `InboxPageV2` again. For six already-imported properties this is a 3,216-line, 35-file wizard whose most complex code (`IMPORT_RECOVERY_DELAYS_MS`, reload recovery) exists for a page refresh mid-submit.

**Guest: scan QR → rate → submit.** 9 hops and it reads well: QR is client-only (`portal-share/use-qr-code-generation.ts:14-18`, `qrcode` package; there is no QR API route) → `p/$token.tsx:94-98` loader → `PublicPortalView:152-232` wires 8 actions + `recordScanFn` → `guest-analytics-notice.tsx:191-197` → `public-portal-content.tsx:86` → `guest-response-form.tsx:15` → `use-guest-response-controller.ts:39` (only client CSRF state: one nonce string) → `guest-rating-form.tsx` / `guest-private-feedback-form.tsx` → `contexts/guest/server/public.ts:316-658`. 30 files / 1,809 prod lines. Two fragilities for a new developer: `key={token}` at `$token.tsx:149` is the only thing preventing nonce/draft leakage between portals and nothing tests it; `public-portal-content.tsx:86` serves both the anonymous guest and the authenticated manager preview through one `token !== undefined` ternary. This journey is the template the other two should be cut down to.
